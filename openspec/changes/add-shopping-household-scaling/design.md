## Context

動機は proposal.md の Why を参照。

- S07 は `ShoppingService.List` が献立と在庫から毎回算出し、保存しない。計上の単位は `(batch_id, recipe_id)` の組で、作り置きは 1 回分だけ数える
- `PlannedBatch.BatchMemberCount` は `batch_id` 全体の行数で、別のレシピの行も数える (時間帯全体の作り置きコピーで 1 つの作り置きに複数のレシピが入る)
- レシピの人数は `recipes.servings` (1〜99、NOT NULL)
- S09 の値は `settings` テーブルに既定値から変えた key だけを持ち、各サービスは `configSource.current()` で読む (design.md §5)

## Goals / Non-Goals

**Goals:**

- 家族の人数で買う量の目安が合うようにする
- ひとりの作り置き型の既定の動きを変えない (既定は換算しない)

**Non-Goals:**

- 作り置きと在庫の消費の換算 (proposal.md の Non-goals)

## Decisions

### D1. 換算する献立の範囲

**選択肢:**

- (a) すべての `(batch, recipe)` を換算する — Pros: 規則が単純 /
  Cons: 1 人で 4 人分のカレーを 3 日かけて食べる作り置きが、世帯人数 1 で 1/4 に減る。作り置きのペルソナで必要量が大きく外れる
- (b) 同じ `(batch, recipe)` の行が献立全体で 1 行だけのときに換算する ← 採用 — Pros: 1 回で食べきる献立だけが換算され、作り置きは書いた量のまま /
  Cons: 2 日分の作り置きを 4 人家族で作ると、レシピが 2 人分なら量が足りない。利用者がレシピの人数か量を直す必要がある
- (c) 作り置きは「世帯人数 × 日数 ÷ レシピの人数」で換算する — Pros: 理屈の上では正しい /
  Cons: 作り置きは「多めに作って数日もたせる」運用で、1 日に食べる量が人数分とは限らない。過大な量を出しやすい

**採用: (b)**。理由: 換算を外したときの誤差より、換算を入れたときの誤差のほうが大きくなる場面を避ける。作り置きの扱いは後続に残す。

「1 行だけ」は期間の内外を問わず数える。期間の境界で作り置きが切れていても、1 回きりの献立と取り違えないようにするためである。
`batch_id` 全体の行数 (`BatchMemberCount`) ではなく、同じレシピの行数 (`PairRowCount`) で判定する。
時間帯全体を 1 日だけ持つ作り置き (別のレシピと同じ `batch_id`) も、そのレシピとしては 1 回きりだからである。

### D2. 換算の計算と丸め

量のある材料の量に `世帯人数 / servings` を掛け、合算のあとで既存の `roundAmount` で丸める (合算前に丸めると誤差が積み上がる)。
量を持たない材料 (量 0 と量る単位の材料) は換算しない。量る単位の材料は合算の時点で量 0 に落とすので、換算の有無が結果に出ない。

換算は `Aggregate` の中で、材料を合算のキーに入れる直前に行う。`scale.go` の純関数 `ScaledAmount(amount, servings, household, pairRowCount)` にし、table-driven で確かめる。

### D3. 設定の値: 0 を「換算しない」とする

`HouseholdServings int`。0 は換算しない、1〜10 は世帯人数。

**選択肢:**

- (a) `*int` で nil を換算しない — Pros: 意味が型に出る / Cons: JSON の null とフロントの select の扱いが増える。既存の Values はすべて非 nil の値
- (b) 0 を換算しない ← 採用 — Pros: 既存の int の設定と同じ扱いで保存と検証ができる / Cons: 0 の意味を知っている必要がある

**採用: (b)**。理由: S09 の select の先頭を「換算しない」(値 0) にすれば、画面からは 0 の意味を意識しない。

上限の 10 は、家庭の人数として十分で、select の選択肢を短く保てる値として置く。

### D4. 換算したことの表示

`List.ScaledServings` に、換算した材料が 1 件でもあれば世帯人数を、無ければ 0 を入れる。
S07 は 0 でないとき、対象期間の下に注記を出す。行ごとの印は付けない (換算した行と換算していない行が合算されうるため、行単位では言い切れない)。

### D5. 一括登録とテキストでコピー

どちらも `List.Items[].Amount` を使っているので、換算後の量がそのまま入る。追加の分岐は置かない。

## Risks / Trade-offs

- [Risk] 世帯人数を変えたことを忘れ、S07 の量がレシピと違う理由が分からなくなる → D4 の注記を S07 に常に出す
- [Risk] `add-mealplan-suggest-by-time` も `S09 設定画面の表示` と `設定値の検証` を MODIFIED にする。先に archive した側の内容を、後の側が取り込んでから archive する
  → 後に archive する change の delta を、先の archive 後の spec.md に合わせて書き直す (openspec-update-change)
- [Risk] 小数の「個」(1.5 個) が出る → 目安として扱う既存の方針 (product.md S07) のまま。丸めの規則は後続で決める
