## Context

動機は [proposal.md](proposal.md) の Why を、受け入れ条件は [specs/mealplan/spec.md](specs/mealplan/spec.md) を参照。

現状の品行は次の構成である (`meal-plan-cell.tsx`)。

```
品行 (div, draggable は単独の品だけ)
├─ 🔗 (作り置きの品だけ)
├─ 作った印のチェック (印の付いた品だけ、表示のみ)
├─ レシピ名 (1 行で省略)
└─ ⋯ (Radix の DropdownMenuTrigger)
```

試作では、アプリのコードを変えずにブラウザ側で CSS を上書きし、1 セルの幅とレシピ名に残る幅を測った。
1088px の画面 (1920×1080、拡大率 100%) での内訳は次のとおりである。

| 要素 | 幅 |
|---|---|
| 1 セル | 94px |
| セルの枠と内側の余白 (`p-3`) | 29px |
| 品行の枠と左右の余白 | 11px |
| `⋯` と間隔 | 31px |
| レシピ名 (単独の品) | 23px |

ルートの文字サイズ 18px と Wails の Zoom 1.5 が掛け合わさり、rem で決めた余白は物理ピクセルで 1.5 倍になる。
時間帯ラベルの列も 6rem (108px) を取っている。

Radix の `DropdownMenuTrigger` は、マウスのボタンを押し下げた時点 (`pointerdown`) でメニューを開く。
インストール済みの `@radix-ui/react-dropdown-menu` 2.1.24 のソースで確かめた。

## Goals / Non-Goals

**Goals:**

- 1088px の画面で、単独の品も作り置きの品も、レシピ名をおよそ 3〜4 字×2 行まで読めるようにする
- 作った印を 1 クリックで付け外しできるようにする
- 品のメニューを、狙いにくい `⋯` ではなく品行のクリックで開けるようにする
- 単独の品の D&D を、これまでどおり使えるようにする

**Non-Goals:**

- サイドバー、ルートの文字サイズ、Zoom の見直し (proposal の Non-goals を参照)
- 作り置きの品の D&D (作り置き全体を動かす操作は R7 で扱う)

## Decisions

### D1. 品のメニューの開き方

**選択肢:**

- (a) 品行そのものを `DropdownMenuTrigger` にする
  — Pros: 部品の使い方が今と同じ
  / Cons: ボタンを押し下げた時点でメニューが開くので、ドラッグしようとするたびにメニューが開く
- (b) メニューの開閉を自前の状態で持ち、レシピ名のボタンの `click` で開く。`DropdownMenuTrigger` は表示位置の基準にだけ使う ← 採用
  — Pros: ブラウザの D&D では、ドラッグが始まると `click` が発火しないので、クリックとドラッグを区別できる
  / Cons: 基準にする `DropdownMenuTrigger` の置き方を決める必要がある
- (c) Radix の Popover の中に項目を並べる
  — Pros: Popover は基準の要素 (Anchor) を自由に指定できる
  / Cons: メニューのキーボード操作 (矢印キーでの移動、項目の役割) を自前で作ることになる

**採用: (b)**。
基準にする `DropdownMenuTrigger` は、品行に重ねた透明な要素とし、`pointer-events: none` でマウスの操作を受けないようにする。
こうすると、Radix が `pointerdown` で開く処理は働かず、位置の計算だけが品行に合う。
メニューは `side="right"` で開く。Radix は画面の端で収まらないときに反対側へ回り込むので、左に開く処理は自前で書かない。
メニューを閉じたときは、フォーカスをレシピ名のボタンに戻す。

この置き方で位置と開閉が期待どおりに動くかは、実装の最初に小さく試す (tasks.md 1.x)。
期待どおりに動かなかった場合は (c) に切り替え、design.md を更新する。

**試作の結果 (tasks.md 1.2)：(b) のまま進める。**
E2E と同じ構成 (headless Chromium、画面幅 1088px と 870px) で試し、次のとおり動いた。

- レシピ名をクリックすると、メニューは品行の右端から 3px 右に、品行の上端とそろえて開く
- 日曜の列の品では、メニューは品行の左に回り込む
- Enter と Space のどちらでもメニューが開き、矢印キーで項目を移れる。Esc で閉じると、フォーカスはレシピ名のボタンに戻る
- メニューの外をクリックすると、何も選ばずに閉じる

実装では次の 2 点を足した。

- 基準の要素は `DropdownMenuTrigger asChild` の `span` とし、`relative` にした品行の直下に `absolute inset-0` で重ねる。
  レシピ名のボタンの中ではなく品行の直下に置くのは、メニューの位置を品行の右端に合わせるためである
- 基準の `span` はフォーカスを受けないので、`onCloseAutoFocus` で Radix の既定の処理を止め、レシピ名のボタンにフォーカスを戻す

メニューが開いている間、Radix はメニュー以外の要素に `aria-hidden` を付ける。
E2E では、メニューを開いたまま `getByRole` で品行を探しても見つからない点に注意する。

### D2. 品行の構成

```
品行 (div, draggable は単独の品だけ)
├─ 「作った」チェックボックス (input type="checkbox")
└─ レシピ名のボタン (button, aria-haspopup="menu", 2 行まで折り返す)
     └─ 位置の基準にする透明な DropdownMenuTrigger
```

レシピ名を `button` にすると、フォーカス、Enter と Space での起動、読み上げ時の役割が揃う。
次の 2 点は確かめていないので、D1 の試作で一緒に確かめる。

- Chromium (WebView2) で、`draggable` な要素の中の `button` からドラッグを始められるか。
  始められない場合は、レシピ名を `role="button"` と `tabIndex` を持つ `span` にし、Enter と Space の処理を自前で書く
- チェックボックスを押したときにドラッグが始まらないか。始まる場合は、チェックボックスに `draggable={false}` を付ける

**試作の結果 (tasks.md 1.2)：**

- headless Chromium では、`draggable` な品行の中の `button` からドラッグを始められた。
  ドラッグした品は別のセルに移り、`click` は発火せず、メニューも開かなかった。レシピ名は `button` のままにする
- チェックボックスを押したまま動かすと、品行のドラッグが始まった。`draggable={false}` を付けても変わらなかった。
  ドラッグの対象は `draggable` な祖先から決まり、子の `draggable={false}` では止まらないためである。
  代わりに、品行の `mousedown` で押した場所がチェックボックスかどうかを覚え、`dragstart` で `preventDefault` する形にした
- 掴んだ時点の品行はホバー中なので、D8 のホバーの背景色がドラッグ中の ghost の緑より優先される。ghost の背景色を important にして保った

WebKit2GTK (`task dev`) と WebView2 (Windows 実機) での確認は残っている (tasks.md 1.2 と 5.8)。

### D3. 作った印のチェックボックス

**選択肢 (表示):**

- (a) すべての品行に常に表示する ← 採用
  — Pros: 押せる場所が常に見え、操作が直感的
  / Cons: レシピ名の幅が 1 字ぶん (約 22px) 減る
- (b) 印の付いた品だけ常に表示し、印の無い品はホバーしたときだけ表示する
  — Pros: レシピ名の幅が広い
  / Cons: 印を付けられることに気づきにくい

**採用: (a)**。利用者と相談して決めた。

**選択肢 (品のメニューの「作った」「作った印を外す」):**

- (a) 品のメニューにも残す
  — Pros: 付け外しの入口が 2 つになる
  / Cons: 同じ操作の入口が 2 つあり、メニューが長くなる
- (b) 品のメニューから外す ← 採用
  — Pros: 入口が 1 つになる。チェックボックスはフォーカスでき、Space で切り替えられるので、キーボードでも操作できる
  / Cons: `add-mealplan-cooked-mark` で入れた項目を外すことになる

**採用: (b)**。

チェックボックスのラベルは既存の `pages.meal_plan.cell.cooked` (「作った」) を使う。
押したときは `add-mealplan-cooked-mark` の `SetCooked` をそのまま呼び、楽観的更新は入れない (同 design.md D6 と同じ理由)。

### D4. 作り置きの見分け方

**選択肢:**

- (a) 🔗 を品行から外し、枠の色だけで見分ける ← 採用
  — Pros: レシピ名の幅がもっとも広がる
  / Cons: 色だけの区別になる
- (b) 🔗 を品行の右上の角に小さく重ねる
  — Pros: 🔗 を残したまま幅を空けられる
  / Cons: 小さな記号がレシピ名の 2 行目と重なりやすい
- (c) 今のまま名前の左に置く
  — Pros: 変更が無い
  / Cons: 作り置きで作った印も付いた品では、名前の幅がもっとも狭くなる

**採用: (a)**。利用者と相談して決めた。
S07 の「この期間の献立」欄は幅に余裕があるので、🔗 を残す。

### D5. レシピ名の折り返し

レシピ名は 2 行まで折り返し、2 行に収まらない分は省略記号で省略する (`line-clamp-2`)。
英字の長い語でも折り返せるよう、`overflow-wrap: anywhere` を付ける。

**選択肢:**

- (a) すべての表示期間と時間帯数で折り返す ← 採用
  — Pros: 挙動が一貫し、密度の高い表示でも名前が読める
  / Cons: カレンダーの縦の長さが伸びる
- (b) 1 週表示だけ折り返す
  — Pros: 2 週と 4 週の縦の長さは今と変わらない
  / Cons: 密度の高い表示では名前がほとんど読めない

**採用: (a)**。利用者と相談して決めた。
試作の実測では、カレンダーの縦の長さは 1 週×夕食で +4%、4 週×3 食で +14% になる。
4 週×3 食はもともと縦にスクロールする長さなので、この伸びは受け入れる。
`MealPlanCellSizePresets` の値 (セルの最低の高さ、文字サイズ、表示件数) は変えない。

### D6. 余白と時間帯ラベルの列幅

次の 3 か所を詰める。

- セルの内側の余白：`p-3` (1 週) と `p-2` (4 週) を `p-1` にする
- 品行の左右の余白：`px-1` を `px-0.5` にする
- 時間帯ラベルの列：`6rem` を `2.5rem` にする (「夕食」のような 2 字のラベルが収まる幅)

S01 のページの余白 (`p-6`) は、他の画面とそろえるために変えない。
これらの値は利用者が設定で変える値ではないので、`internal/config/defaults.go` には置かない。

### D7. ワイヤーとの差分

`docs/wireframes/S01_meal_calendar.v2.drawio.svg` は、品行の左端の色帯と 🔗 で作り置きを示し、作った印のチェックの印を描いている。
[docs/wireframes/README.md](../../../docs/wireframes/README.md) の方針どおり、ワイヤー本体は更新せず、差分をここに残す。

- 作り置きは枠の色だけで示し、🔗 は品行に描かない
- 品行の左端に、すべての品で「作った」チェックボックスを置く
- 品行の右端の `⋯` は置かず、レシピ名のクリックで品のメニューを開く
- レシピ名は 2 行まで折り返す

画面の構造そのもの (7 列の並べ方、セルの中の縦積み) は変わらないので、v3 のワイヤーは作らない。

### D8. 品行のカーソルとホバー時の表示

**選択肢:**

- (a) ドラッグできる品行はつかむ形 (`grab`)、作り置きの品行はポインタにする
  — Pros: ドラッグできるかどうかがカーソルで分かる
  / Cons: 主な操作であるクリックが、`grab` のカーソルからは読み取れない
- (b) すべての品行をポインタにし、ホバーで背景色を変える ← 採用
  — Pros: どの品行もクリックでメニューが開くことが、一つの表示で伝わる
  / Cons: ドラッグできるかどうかは、カーソルでは分からなくなる

**採用: (b)**。
作り置きの品行を `cursor-not-allowed` にする今の表示は、クリックできる品行と矛盾するのでやめる。
ホバー時の背景色は薄い青 (`bg-blue-100`) にする。
最初は薄い灰色 (`bg-neutral-100`) にしたが、白いセルの上では差が小さく、クリックできることが伝わりにくかった。
青は期間切替などの操作できる部品と同じ系統の色で、作り置きの枠色 (橙、緑、紫) やドラッグ中の ghost の緑とも重ならない。

## Risks / Trade-offs

- [Risk] D1 (b) の置き方で、メニューの位置がずれる、または Radix のフォーカス管理と噛み合わない
  → 実装の最初に小さく試し、だめなら D1 (c) に切り替えて design.md を更新する
- [Risk] チェックボックスを押し間違えて印を付けてしまう → もう一度押せば外れる。チェックボックスとレシピ名のボタンは別の要素なので、名前を押して誤って印が付くことは無い
- [Risk] 色だけでは作り置きを見分けにくい人がいる → 枠の色は 2〜3 色の線で、背景色ではない。S07 の献立欄には 🔗 が残る。
  見分けにくいという声が出たら、枠の線の種類 (実線と破線) を足すことを検討する
- [Risk] 品行がクリックできることに気づかれない → ホバー時の背景色とポインタのカーソルで示す (D8)
- [Risk] 870px の画面 (拡大率 125%) では、名前はおよそ 2 字×2 行にとどまる → サイドバーと Zoom の見直しを後続の proposal に回す
- [Risk] クリックとドラッグの区別は Playwright の D&D では確かめられない (既存の D&D の E2E も skip) → Windows 実機で確かめる (tasks.md 5.8)
- [Risk] `revise-mealplan-reorder-menu` と同じ要件 (「セル内の品表示」) とファイル (`cell-item-menu.tsx`) を変える
  → 後から archive する側で delta を合成し直す。「上へ移動」「下へ移動」は品のメニューの項目としてそのまま入る
