## Context

動機は proposal.md の Why を参照。

- S02 は `RecipeService.List` の結果 (タグを含む) を取得し、名前の部分一致と並び替えをフロントで行っている (`routes/recipes.tsx`)
- 検索語と並び順は route の search param (`q` / `sort`) に持ち、S03 の開いた元 (`detail-origin.ts`) にも渡して、戻ったときに復元している (revise-recipe-detail-page D3)
- サイドバーから開くと search param が無く、既定 (空、更新日 降順) になる
- タグは `RecipeTagsInput` で自由に付けられ、前後の空白を除いて保存される

## Goals / Non-Goals

**Goals:**

- 名前を覚えていないレシピを、タグを 1〜2 回押すだけで探せるようにする
- 既存の検索語と並び順の保ち方と同じ仕組みに載せる

**Non-Goals:**

- 材料名、OR 条件、S01 のダイアログ (proposal.md の Non-goals)

## Decisions

### D1. 選び方: チップを並べる

**選択肢:**

- (a) 全タグのチップを並べ、押して切り替える ← 採用 — Pros: 1 回押すだけで絞れる。どんなタグがあるかが見える /
  Cons: タグが増えると場所を取る
- (b) 「タグ」のドロップダウンにチェックボックスを並べる — Pros: 場所を取らない / Cons: 開く、選ぶ、閉じるで 3 動作になる。選んでいるタグが閉じると見えにくい
- (c) 検索欄に `#和食` と書くとタグとして扱う — Pros: 欄が増えない / Cons: 記法を知らないと使えない

**採用: (a)**。理由: ペルソナのレパートリー (20〜50 品) ではタグは 10 前後に収まり、並べても邪魔にならない。増えたときの扱いは後続に残す。

### D2. 条件: すべてのタグを持つ (AND)

**選択肢:**

- (a) AND ← 採用 — Pros: 選ぶほど絞れる。名前の検索と組み合わせたときも「全条件を満たす」で一貫する / Cons: 「和食か中華」は一度に出せない
- (b) OR — Pros: 気分の候補を広く出せる / Cons: 名前の検索 (AND で効く) と組み合わせたときの結果が読みにくい

**採用: (a)**。

### D3. タグの比べ方と一覧

タグは保存された文字列のまま、完全一致で比べる (大文字と小文字、ひらがなとカタカナをそろえない)。
食材名のようにそろえると、「Easy」と「easy」を同じチップにまとめる表示名の規則が要る。タグは利用者が選んで付けるので、揺れは S04 で直してもらう。

チップの一覧は、削除済みでないレシピのタグの和集合を `localeCompare` (ja) の昇順に並べる。件数は添えない。
選んでいたタグを持つレシピがすべて削除された場合は、そのタグを選択から外す。

### D4. 状態の持ち方: search param の `tags`

`recipesSearchSchema` に `tags: z.array(z.string()).optional().catch(undefined)` を足し、`q` / `sort` と同じく `detail-origin.ts` で S03 に渡して戻す。

他案として `useState` だけに持つことも検討したが、S03 から戻ると消えるので、検索語と並び順だけ戻ってタグが消える不揃いが起きる。

### D5. 絞り込みの関数を切り出す

名前の検索とタグの絞り込みを `recipe-filter.ts` の `filterRecipes(recipes, { query, tags })` にまとめ、Vitest の table-driven で確かめる。
`routes/recipes.tsx` の `useMemo` はこの関数と既存の `compareRecipes` を呼ぶだけにする。

## Risks / Trade-offs

- [Risk] 表記の違うタグ (「簡単」と「かんたん」) が別のチップになる → D3 のとおり、S04 で直す運用にする。チップに並ぶことで揺れに気付きやすくなる
- [Risk] タグが多いと S02 の上部が縦に伸びる → 折り返して表示し、30 を超える場合の扱いは後続に残す
