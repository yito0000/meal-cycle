## Context

動機は [proposal.md](proposal.md) の Why を、受け入れ条件は [specs/shopping/spec.md](specs/shopping/spec.md) を参照。

S07 と S05 / S06 は、同じ `stock_items` を別々のサービスから触っている。設計を縛るのは次の現状である。

- `ShoppingService.List` は開くたびに献立と在庫から算出し、何も保存しない。材料の行は「食材名 + 単位」の組で一意になる
- 在庫の追加は `FridgeService.Add` が 1 行ずつ行う。入力の検証 (`validateStockInput`) と上限値は `internal/service/fridge.go` にあり、
  フロントの `frontend/src/components/fridge/stock-form.ts` が同じ規則を写している
- `StockRepo` の挿入は `insertStockItem(ctx, execer, item)` に切り出されていて、`*sql.DB` でも `*sql.Tx` でも呼べる
- S07 の一覧は `useShoppingList` が `["shopping", periodStart, periodDays]` をキーに取得する。
  在庫の mutation は `["fridge", "list"]` と `["fridge", "suggestions"]` だけを invalidate している
- S06 の賞味期限欄はネイティブの `<input type="date">` である。
  アプリ内の `DatePicker` (S07 の開始日で使用) は値が必須で、空の賞味期限を表せない

## Goals / Non-Goals

**Goals:**

- 一括登録を「全部入るか、何も入らないか」のどちらかにする。途中まで入った状態を利用者に見せない
- 在庫の入力規則を S06 と共有し、規則の写しを増やさない
- チェック状態を S07 の画面の中だけで完結させ、Go 側にも DB にも新しい状態を持ち込まない

**Non-Goals:**

- 一括登録の性能の最適化。1 回の登録は多くて数十行で、1 トランザクションの逐次 INSERT で足りる
- ダイアログの行の並び替えや、同じ食材の行の自動結合

## Decisions

### D1. 一括登録の API の置き場所

**選択肢:**

- (a) フロントから `FridgeService.Add` を行の数だけ呼ぶ
  — Pros: Go 側の追加が無い
  / Cons: 3 行目で失敗すると 1、2 行目だけが在庫に残る。どこまで入ったかを利用者に伝える UI が要る。行の数だけ IPC が往復する
- (b) `FridgeService.AddMany` を追加し、全行を検証してから 1 トランザクションで挿入する ← 採用
  — Pros: 全部入るか何も入らないかが DB の単位で保証される。検証は既存の `validateStockInput` をそのまま使える
  / Cons: fridge のサービスに、S07 からしか呼ばれないメソッドが 1 つ増える
- (c) `ShoppingService.RegisterPurchases` を追加する
  — Pros: S07 の操作が S07 のサービスに閉じる
  / Cons: shopping のサービスが在庫の書き込みと検証を持つことになり、在庫の規則が 2 つのサービスに分かれる

**採用: (b)**。書き込む対象は在庫であり、規則の持ち主も fridge である。
呼び出し元が S07 だけであることは、在庫を複数行まとめて足すという操作の性質を変えない。
`StockRepo` には `CreateMany(ctx, inputs []fridge.StockItem) ([]fridge.StockItem, error)` を足し、
トランザクションの中で既存の `insertStockItem` を行の数だけ呼ぶ。
ID は行ごとに `uuid.NewV7()` で発行し、`AddedAt` と `UpdatedAt` は全行で同じ時刻にする。

### D2. `AddMany` の検証とエラー

**選択肢:**

- (a) 最初に見つかった不正な行のエラーを返す。エラーは既存の sentinel を `fmt.Errorf("row %d: %w", i, err)` で包む ← 採用
  — Pros: `errors.Is` で sentinel を判定でき、フロントの `stockErrorOf` (メッセージの部分一致) もそのまま効く
  / Cons: 2 行目以降の不正はまとめて返らない
- (b) 行ごとのエラーを型付きの配列で返す
  — Pros: サーバ側の検証結果だけで全行のエラーを表示できる
  / Cons: Wails のバインディングにエラー用の型が増える。フロントは同じ規則で事前に検証するため、この情報を使う場面がほぼ無い

**採用: (a)**。フロントは登録を送る前に全行を `validateStockForm` で検証し、行ごとのエラーを表示する (D5)。
サーバの検証はフロントとの規則のずれを防ぐ最後の関門であり、ここに届くエラーはダイアログ上部に 1 件だけ出せば足りる。
空の配列を渡されたときはエラーにせず、空の配列を返す。UI はチェック 0 件でボタンを押せないので、この経路は通常通らない。

### D3. チェック状態の持ち方

**選択肢:**

- (a) `ShoppingPage` の `useState<Set<string>>` で、材料の行のキー (`name + "\u0000" + unit`) の集合を持つ ← 採用
  — Pros: 表示中の行と 1 対 1 に対応し、画面を離れれば自然に消える (proposal の Non-goals と一致)
  / Cons: 一覧が再取得されて行が消えたとき、集合に残ったキーを掃除する必要がある
- (b) 行のインデックスで持つ
  — Pros: 実装が短い
  / Cons: 登録後の再算出で並び順が変わる (在庫ありの行が末尾に移る) と、別の行にチェックが付いたように見える

**採用: (a)**。キーは `ShoppingTable` がすでに行の React key に使っている組と同じにする。
期間を切り替えたときは、`periodStart` と `periodDays` の組が変わったら集合を空にする。
この組を `useState` の初期化キーとして保持し、描画時に前回の組と比べて空にする (React の「props の変化で state をリセットする」形)。
件数とダイアログの行は、集合を現在の `items` と突き合わせてから数える。
一覧に無いキーが集合に残っていても、件数にもダイアログにも出ない。

### D4. 全選択の見出しチェックボックス

**選択肢:**

- (a) 見出しにチェックボックスを置き、一部だけチェックがあるときは indeterminate を表示する ← 採用
  — Pros: 表計算やメールの一覧と同じ見た目で、説明が要らない
  / Cons: indeterminate は属性ではなく DOM プロパティなので、ref で設定する必要がある
- (b) テーブルの上に「すべて選択」「すべて解除」のボタンを 2 つ置く
  — Pros: 状態の説明が要らない / Cons: ワイヤーにある列の構成から外れ、画面上部の要素が増える

**採用: (a)**。押したときの挙動は spec のとおり、全行にチェックがあるときだけ全解除、それ以外は全選択とする。
既存の S01 のチェックボックス (`meal-visibility-checkboxes.tsx`) と同じく、shadcn の Checkbox は入れずネイティブの
`<input type="checkbox">` を使う。見出しと各行には `aria-label` を付け、E2E はそれで要素を取る。

### D5. ダイアログの入力欄と検証の共有

**選択肢:**

- (a) S06 の `stock-form.ts` (`StockFormValues` / `validateStockForm` / `toStockInput`) を行ごとに再利用する ← 採用
  — Pros: 規則の写しが増えない。エラーの i18n キーも `pages.fridge.errors.*` を共有できる
  / Cons: shopping のコンポーネントが fridge のモジュールに依存する
- (b) shopping 側に専用の検証を書く — Pros: 依存が無い / Cons: 上限値と文言が 3 か所目の写しになる

**採用: (a)**。`purchase-form.ts` は、チェックした `Item` の配列から `StockFormValues[]` の初期値を作る関数と、
全行を検証して行ごとの `StockFormErrors` を返す関数だけを持つ。
量の初期値は `formatAmount` で文字列にする (小数第 2 位で丸め、末尾の 0 を省く)。必要量が 0 なら空文字にする。
賞味期限の欄は S06 に揃えてネイティブの `<input type="date">` を使う。`DatePicker` は空の値を扱えないため使わない。

### D6. 登録後の再取得と通知

**選択肢:**

- (a) `AddMany` の成功時に `["fridge"]` 系のキーと `["shopping"]` の前方一致キーを invalidate する ← 採用
  — Pros: S07 がその場で算出し直し、在庫の状態が変わる。S05 を開いたときにも最新の一覧が出る
  / Cons: S07 の既存のコメント「在庫の mutation からは invalidate しない」と方針が変わる
- (b) S07 の一覧を楽観的に書き換える — Pros: 再取得の往復が無い
  / Cons: 在庫の状態判定をフロントでやり直すことになり、Go の集計と二重になる

**採用: (a)**。既存のコメントは S05 からの変更を念頭に置いたもので、S07 自身の操作の結果は S07 にすぐ映すべきである。
`use-shopping-list.ts` のコメントを「他画面の mutation からは invalidate しない」に直す。
fridge の invalidate は `use-fridge.ts` の `useInvalidateFridge` を export して使い回す。
成功時の処理は `ShoppingPage` が持つ。ダイアログを閉じ、チェックの集合を空にし、
sonner の `toast` で「N 件を冷蔵庫に登録しました」を出す。取り消しの操作はトーストに付けない (proposal の Non-goals)。
失敗時はダイアログを開いたまま、`stockErrorOf` で引いた文言をダイアログ上部に出す。

### D7. ダイアログの行の並びと編集の範囲

ダイアログの行は、ボタンを押した時点の材料テーブルの並び (在庫の状態、最初に必要になる日、食材名、単位の順) を写す。
行の追加と削除は受け付けない (proposal の Non-goals)。
ダイアログを開いたあとに材料テーブル側が変わっても、ダイアログの行は開いた時点の値のまま保つ。
開くたびに初期値から作り直すので、キャンセルして開き直すと編集中の値は捨てられる。
他の案として、編集中の値をチェックの集合と一緒に保持して開き直しても残す形も考えたが、
キャンセルを「なかったことにする」操作と読むほうが自然であり、状態も増えないため採らなかった。

## Risks / Trade-offs

- [チェック状態が画面遷移で消えるため、S05 で在庫を確かめてから戻るとチェックを付け直すことになる]
  → 帰宅後に手元の食材を見ながら一度に付ける使い方を想定しており、行き来は少ない。
  不満が出たら、期間をキーにした sessionStorage への退避を検討する
- [ダイアログの量の初期値が必要量のため、実際に買った量 (1 袋、1 パック) と単位が合わないことが多い]
  → 量も単位も編集できるようにしている。単位を変えると S07 の突き合わせ (食材名 + 単位) では在庫として数えられなくなるが、
  これは S06 から入力した場合と同じ挙動であり、spec の「単位が違う在庫は在庫として扱わない」に従う
- [`AddMany` を fridge に置くと、S05 の画面からは使わないメソッドが FridgeService に残る]
  → メソッドのコメントに、S07 の一括登録から呼ばれることと、全行を 1 トランザクションで入れる理由を 1 行で残す
- [一括登録で行数が多いと、ダイアログが縦に長くなる]
  → ダイアログの本体に最大の高さを設けて縦にスクロールさせ、登録とキャンセルのボタンは常に見える位置に置く

## Migration Plan

スキーマの変更は無い。既存の DB にそのまま適用でき、戻すときもコードを戻すだけで済む。
