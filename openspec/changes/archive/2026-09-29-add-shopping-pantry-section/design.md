## Context

動機は [proposal.md](proposal.md) の Why を、受け入れ条件は [specs/shopping/spec.md](specs/shopping/spec.md) を参照。

`add-measuring-units` の実装後、S07 の状態は次のとおりである。

- `ShoppingService.List` の `items` には、量を持たない材料も 1 行として含まれる。
  その行は単位が空で必要量が 0、在庫の状態は `none` か `covered` のどちらかになる
- 逆に、必要量が 0 の行は量を持たない材料の行だけである。単位の無い量のある材料に合算された行は、必要量が 0 より大きい
- 並び順は Go 側で決まる。`covered` 以外が先、`covered` が後で、それぞれ最初に必要になる日、食材名、単位の順
- `ShoppingPage` は `data.items` をそのまま、テーブル、絞り込みの件数、チェックの集合との突き合わせに使っている
- ワイヤー `S07_shopping_list.v2.drawio.svg` には、材料テーブルと献立の欄だけが描かれている

## Goals / Non-Goals

**Goals:**

- 量を持たない材料をフロントの表示だけで材料テーブルから外し、Go 側とバインディングに手を入れない
- 材料テーブル、絞り込み、チェック、一括登録が、量のある材料だけを前提にできるようにする

**Non-Goals:**

- 量を持たない材料の判定規則を変えること (`add-measuring-units` のとおり)
- 別の欄を折りたたんだり、材料ごとに欄を選んだりすること

## Decisions

### D1. 量を持たない材料を分ける場所

**選択肢:**

- (a) フロントで `data.items` を `amount === 0` で分ける ← 採用
  — Pros: Go 側とバインディングが変わらない。Context のとおり、必要量 0 の行と量を持たない材料の行は一致する
  / Cons: 「必要量 0 = 量を持たない材料」という Go 側の性質にフロントが依存する
- (b) `shopping.List` に量を持たない材料の配列を別に持たせる
  — Pros: フロントが判定に依存しない
  / Cons: バインディングと e2e の shim が変わる。在庫の状態と並び順の算出を 2 つの配列で分けて持つことになる

**採用: (a)**。依存する性質は `internal/domain/shopping/aggregate.go` のコメントと `aggregate_test.go` のケースで固定されている。
判定は `frontend/src/components/shopping/pantry.ts` の `isPantryItem(item)` 1 か所に置き、画面はこの関数だけを見る。

### D2. 別の欄の置き場所と形

材料テーブルと登録ボタンの下、左の列 (材料の列) の中に置く。
狭い画面では献立の欄が材料の列の下に回るので、別の欄は献立の欄より上に来る。

他の案として、右の列 (献立の欄の上) に置くことも考えた。
だが右の列は「この期間の献立」という参照用の欄で、材料を並べると材料と献立の区別が崩れる。
材料テーブルの続きとして読めるよう、左の列に置く。

1 項目は食材名と用途の 2 つだけを並べるリストにする (テーブルにはしない)。
列見出しを持つテーブルにすると、必要量と在庫の列が無いことが欠けて見えるためである。
「在庫あり」の項目は材料テーブルの「在庫あり」の行と同じく薄い文字にし、`StockStatusBadge` を小さく添える。
「在庫なし」の項目には何も添えない。調味料は S05 に登録しないことが多く、「在庫なし」の印は情報にならないためである。
各項目に `data-testid="shopping-pantry-item"` と `data-stock-status` を付ける。

### D3. 並び順

Go 側の並び順 (`covered` 以外が先、`covered` が後、それぞれ最初に必要になる日、食材名) をそのまま使う。
量を持たない材料の行は単位が空で、在庫の状態は `none` か `covered` なので、spec の並び順とそのまま一致する。
フロントで並べ替えない。

### D4. テーブル、絞り込み、チェック、空状態の対象

`ShoppingPage` で `data.items` を `tableItems` (量のある材料) と `pantryItems` (量を持たない材料) に分ける。
次の箇所は、これまで `data.items` を見ていたところを `tableItems` に替える。

- 材料テーブルに渡す行 (絞り込みの前)
- `countByStockFilter` の件数
- `checkedItems` (登録ボタンの件数とダイアログの行)
- 材料テーブル、絞り込み、登録ボタンを出すかどうかの判定 (`tableItems.length > 0`)

空状態の判定は次の順に行う。

1. 献立が無い：これまでどおり `empty.no_plans`
2. 材料が無い (`data.items.length === 0`)：これまでどおり `empty.no_ingredients`
3. 量のある材料が無い (`tableItems.length === 0`)：`empty.no_quantified` を材料テーブルの位置に出し、その下に別の欄を出す
4. それ以外：材料テーブル、絞り込み、登録ボタン、別の欄 (`pantryItems.length > 0` のとき)

### D5. 成り立たなくなるシナリオの扱い

「量の指定が無い材料」と「冷蔵庫への一括登録」には、必要量「—」の表示と、量を空にする初期値のシナリオがある。
どちらも本 change で成り立たなくなる。

**選択肢:**

- (a) MODIFIED でシナリオを削除する
  — Pros: 要件名が変わらず、E2E の describe 名も変わらない
  / Cons: `openspec validate` が「MODIFIED で既存のシナリオを落とした」として拒否する。archive で黙ってシナリオが消えるのを防ぐための検査で、回避できない
- (b) シナリオの名前を残し、中身を新しい挙動に書き換える
  — Pros: 検査は通る
  / Cons: 「量の指定が無い材料は量が空になる」のように、名前と中身が食い違う
- (c) 旧名の要件を REMOVED にし、中身を引き継いだ要件を新しい名前で ADDED する ← 採用
  — Pros: 削除の理由が REMOVED の Reason に残る。名前と中身が一致する
  / Cons: E2E の describe 名と、要件を参照する他の要件の文言を改める必要がある

**採用: (c)**。新しい名前は「量を持たない材料の欄」と「チェックした材料の冷蔵庫への一括登録」とする。
同名で REMOVED と ADDED を並べる形は validate が拒否するので、名前を変える。
「同一食材の合算」と「在庫の状態表示」は旧名を参照しているので、MODIFIED で文言だけ改める。

### D6. 不要になる分岐

材料テーブルに必要量 0 の行が来なくなるので、次の分岐を消す。

- `shopping-table.tsx` の、必要量 0 の行に `amount_unspecified` (「—」) を出す分岐
- `purchase-form.ts` の、必要量 0 の行の量を空にする初期値
- ロケールの `pages.shopping.amount_unspecified`

残しておいても害は無いが、到達しない分岐はあとで読む人に「必要量 0 の行がテーブルに来る場合がある」と誤読させる。

### D7. ワイヤーとの差分

`S07_shopping_list.v2.drawio.svg` には別の欄が無い。
画面の構造 (左に材料、右に献立) は変わらず、左の列の末尾に欄が 1 つ増えるだけなので、
[docs/wireframes/README.md](../../../docs/wireframes/README.md) の方針どおりワイヤーは更新せず、この節を差分の記録とする。

## Risks / Trade-offs

- [「牛乳 1 カップ」のように傷みやすい材料が別の欄に入り、在庫の印が無いので買い忘れる]
  → 別の欄にも食材名は必ず出る。不満が出たら、材料ごとに欄を選ぶ案を後続で検討する (proposal の引き継ぎ)
- [Go 側で量を持たない材料の行が必要量 0 でなくなる変更が入ると、フロントの分け方が崩れる]
  → 判定を `isPantryItem` の 1 か所に置き、`aggregate_test.go` のケースと E2E で両側から固定する
- [要件名を付け替えたことで、過去の archive の記述と現行 spec の名前が一致しなくなる]
  → REMOVED の Reason と Migration に新しい名前を書く

## Migration Plan

スキーマとバインディングの変更は無い。既存のレシピと在庫のデータは書き換えず、S07 の表示だけが変わる。
