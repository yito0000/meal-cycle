## Context

- 動機は [proposal.md](proposal.md) 参照
- 現行の 2 経路 (連続 N 日 / 別時間帯) は、ユーザーメンタルモデル (「同じ作り置きを複数セルに広げる」)
  から見ると 1 つの操作。UI が分岐しているのは実装の都合 (CopyLeftover が同 meal 前提、
  CopyToOtherMeal が別 meal 前提) の露出
- サーバ側は既に 2 メソッドで実装済み。今回の統合は UI レイヤに閉じる

## Goals / Non-Goals

**Goals:**

- 「作り置きを広げる」1 操作で (対象日, 対象時間帯) の任意組み合わせを反映できる UX にする
- 既存の作り置き / 別調理選択、衝突解決 (追加 / 上書き / キャンセル) の意味を保つ
- サーバ API は変更しない (UI の変更に閉じる)

**Non-Goals:**

- 時間帯全体コピー (`セル右下 ⋯`) の UX 統合
- CopyLeftover / CopyToOtherMeal のサーバ API 統合
- ドラッグ&ドロップ / カレンダー直接操作による選択

## Decisions

### D1. 選択 UI の形

**選択肢:**

- (a) **格子 (行 = 対象日、列 = 対象時間帯) チェックボックス** ← 採用 — Pros: 空間認知が
  カレンダーと一致、複数選択の視認性が高い、既定チェック済みで「連続 N 日」の 1 クリック相当も
  維持できる。Cons: 対象日 9 行 × 対象時間帯 3 列 = 27 セル、初見で圧倒される可能性
- (b) 対象日リスト + 各行に「時間帯」ドロップダウン — Cons: 対象日ごとに時間帯を選ぶ形になり、
  複数の時間帯を 1 日に選べない
- (c) 対象時間帯セグメント + 対象日 chip 群 — Cons: 「時間帯を切り替えるたびに対象日をチェックし直す」
  操作感になり、格子より劣る
- (d) 「対象日は起点日 +N 日、時間帯は元と同じ or 昼・夜どちらか」の簡易 preset — Cons: 現行の複雑
  ケース (月・火は夕、水は昼) を表現できない

**採用: (a)**。対象日は起点日 ±max(`LeftoverCopyPresets`) 日 (9 行、うち起点日は「元セル」なので
選択不可)、対象時間帯は 3 列。既定は起点日以降の同 meal を `min(LeftoverCopyPresets)` (= 2 日)
だけチェック済みで開く (「1 クリック相当」の維持)。既存割当セルは背景色で示唆する。

### D2. 選択から API 呼び出しへの分解

**選択肢:**

- (a) UI 側で「同 meal 対象日群」と「別 meal 対象セル群」に分けて、それぞれ `CopyLeftover` /
  `CopyToOtherMeal` を並行呼び出し ← 採用 — Pros: サーバ変更ゼロ、既存の衝突解決ロジックを流用
  Cons: 部分成功 (前半だけ成功、後半失敗) の扱いが必要
- (b) 新サービス `SpreadBatch(sourceDate, sourceMeal, sourcePosition, targets: [(date, meal)],
  mode, shareBatch)` を追加 — Pros: 1 トランザクションで反映、部分成功なし。Cons: 実装コスト大、
  既存 API と重複、ロールバック可能性の設計が要る
- (c) 逐次シリアル呼び出し (Promise.all ではなく for await) — Pros: エラーで途中中断できる。
  Cons: 反映速度が遅い

**採用: (a)**。1 品の複製操作なので反映件数は最大 24 セル (9 日 × 3 時間帯 - 1 起点)。並列でも軽い。
部分成功が起きた場合は成功分は残し、失敗分は toast で「N 件の反映に失敗しました」を出す (エラー
コード集約は既存 `errorI18nKey` を流用)。

### D3. 作り置き / 別調理 セグメントの扱い

**選択肢:**

- (a) 現行の CopyModeDialog を廃止し、統合ダイアログ内にセグメントを常設 ← 採用 — Pros: 1
  ダイアログ内で完結
- (b) 既定は「作り置き」で、切り替えたい場合のみ「詳細設定」を展開 — Cons: 「別調理」を選ぶ回数が
  多いユーザーには苦痛
- (c) 選択直後に別ダイアログを開く — 現行の 2 段構造の踏襲になり、統合目的が果たされない

**採用: (a)**。セグメントは常に見える位置に置く。既定は「作り置き」。

### D4. 衝突解決の扱い

**選択肢:**

- (a) チェック時点で衝突セルを視覚提示、`追加 / 上書き` セグメントを常時表示 ← 採用 —
  Pros: 「どこと衝突するか」がその場で分かる、決断コストが減る
- (b) OK 押下時に既存の CopyConflictDialog を挟む — Cons: 2 段構造になる、統合の目的と矛盾
- (c) 衝突セルはチェック不可 — Cons: 「上書きしたい」ユーザーの選択肢を奪う

**採用: (a)**。衝突セルは背景色 (warning tone) で示し、下部の `追加 / 上書き` セグメントで
両方の衝突挙動を選ばせる。ダイアログを閉じるとキャンセル扱い (現行同様)。

### D5. 対象日レンジ

**選択肢:**

- (a) 起点日 ±max(`LeftoverCopyPresets`) 日 — Cons: 9 行になり初見で圧倒される、過去方向はほぼ
  使わない (使用感レビューで指摘)
- (b) 起点日 + 未来 max(`LeftoverCopyPresets`) 日 (5 行) + 「もっと表示」ボタンで拡張 — Cons:
  backend の `CopyLeftover` が `LeftoverCopyPresets = [2,3,4]` の値しか受け付けないため、offset=4
  の同 meal セルを選ぶと `ErrInvalidCopyDays` で失敗する。実装後に発覚
- (c) 起点日 + 未来 max(`LeftoverCopyPresets`) − 1 日 (4 行 = 5 セル) ← 採用 — Pros: backend の
  `CopyLeftover` 許容最大 (offset = max(presets) − 1 = 3) と揃い、どのセルを選んでも失敗しない。
  認知負荷も 4 行に収まる。Cons: 4 日先までしか広げられない (旧仕様の連続 4 日 = 起点 + 3 日先と同じ範囲)
- (d) 起点日から N 日先 (固定) — Cons: N の妥当値は backend 制約と絡む、拡張手段もない

**採用: (c)**。初期表示は起点日 + `max(LeftoverCopyPresets) - 1` = 3 日ぶん = 4 行。過去日への
合流は既存の「他の作り置きにまとめる」メニューでカバーする。より広い範囲 (例: 2 週分に広げる) が
必要になったら、backend `LeftoverCopyPresets` に [5, 6, 7, …] を追加する別 proposal で対応する。
統合ダイアログ側は `expandStepDays > 0` の場合のみ「もっと表示」ボタンを出す作りにしてある
(現状 0 で非表示、backend 拡張後に有効化)。

### D6. 時間帯全体コピー経路と CopyModeDialog の扱い

**選択肢:**

- (a) `CopyModeDialog` を残し、時間帯全体コピー (`セル右下 ⋯ → 時間帯全体を連続 N 日コピー`) 経路の
  「作り置き / 別調理」選択を従来どおりに保つ ← 採用 — Pros: proposal Non-goal
  (時間帯全体コピー UX の統合) を守る、実装差分が最小、既存 UX に影響しない
- (b) 時間帯全体側にも `spread-batch-dialog.tsx` を再利用する — Non-goal に触れるため今回は却下

**採用: (a)**。tasks.md の 4.2 (「`copy-mode-dialog.tsx` を削除する」) は素直に読むと時間帯全体経路を
壊すため、4.3 の判断結果として **削除せず据え置き** で確定する。将来「時間帯全体コピーも統合ダイアログに
寄せる」proposal を別途切ったときに `CopyModeDialog` の去就を再検討する。

## Risks / Trade-offs

- [格子 UI が「連続 N 日」の直感を失う] → 既定チェック (起点日 + 1..N の同 meal を 2 日ぶん) で
  「そのまま OK を押せば連続 2 日」を維持。ユーザーは追加チェックだけで拡張できる
- [部分成功] → 通常はサーバ側バリデーションで弾けないケース (日付レンジ / meal 一致) は UI で
  ガードするため成功する。DB 制約違反等の想定外エラーは「N 件失敗」toast で情報開示
- [対象日 9 行が縦に長い] → ダイアログ高を `max-h-96 overflow-y-auto` にする、または列圧縮
  (行ごとに横 3 列を折り畳む選択肢もあるが、まず素直な格子で試す)

## Migration Plan

- 旧メニュー / 旧ダイアログの削除だけで API 変更なし。既存の e2e テスト名はシナリオ書き換えに合わせて
  更新する
- ロールバック: 統合ダイアログを削り、旧 `⋯ → この品を連続 N 日` / `⋯ → 別の時間帯にも作り置きを追加` /
  CopyModeDialog / CopyToMealDialog を復元すれば元に戻る (Git 履歴から復旧可能)
- i18n key は「削除された key を残さない」方針。ja/en 両方から旧 key を消し、新 key
  (`spread_batch.*`) を足す
