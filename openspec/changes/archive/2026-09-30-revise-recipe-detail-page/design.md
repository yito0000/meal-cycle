## Context

動機は [proposal.md](proposal.md) の Why を、受け入れ条件は [specs/recipe/spec.md](specs/recipe/spec.md) と
[specs/mealplan/spec.md](specs/mealplan/spec.md) を参照。実装に効く現状は次のとおりである。

- S03 は `components/recipe/recipe-detail-drawer.tsx` の 1 部品で、shadcn の Sheet (Radix Dialog) の上に乗っている。
  S02 (`routes/recipes.tsx`) と S01 (`components/mealplan/week-calendar.tsx`) がそれぞれこの部品を描いている
- S02 は開いている S03 のレシピ ID を search の `detail` で持つ。S04 のキャンセルは `/recipes?detail=<id>` に戻して、同じドロワーを開き直している
- S01 は開いている S03 のレシピ ID を `useState` で持ち、URL には載せていない (add-recipe-details D2)
- S02 の検索語と並び順は `useState` で持っている。今はドロワーが S02 の上に重なるだけで S02 がアンマウントされないので、閉じても残る
- S01 の表示期間の開始日は `useState` で持ち、サイドバーから開くたびに今週に戻る。期間長と時間帯表示は localStorage に保存している
- S07 は期間を search の `from` / `days` で受け取り、サイドバーのリンク (search 無し) では既定の期間になる。この形はすでに動いている
- ルータは memory history で、URL は画面に出ない。search はルータ内の状態としてだけ働く
- `components/ui/sheet.tsx` を使っているのは S03 のドロワーだけである

## Goals / Non-Goals

**Goals:**

- S03 を独立したルートにし、S02 と S01 のどちらから開いても同じ画面部品で描く
- 開いた元の画面と、その画面の状態 (S02 の検索語と並び順、S01 の開始日) を、S03 と S04 を行き来しても失わずに持ち回る
- S04 の未保存の確認を、キャンセルとパンくずの両方で同じ規則にする

**Non-Goals:**

- スクロール位置の復元 (proposal の Non-goals)
- サイドバーの選択表示を開いた元に合わせること (D9)
- S04 での Esc キーによる移動 (D5)

## Decisions

### D1. S03 の置き場所

**選択肢:**

- (a) `/recipes/$recipeId` を独立したルートにする ← 採用
  — Pros: S03 が 1 つのルートで完結し、S02 と S01 は画面を移るだけになる。S04 (`/recipes/$recipeId/edit`) と並びがそろう
  / Cons: S02 と S01 がアンマウントされるので、開く前の状態を URL で持ち回る必要がある (D3 / D4)
- (b) `/recipes?detail=<id>` のまま、S02 の中身を一覧から詳細に差し替える
  — Pros: ルートが増えない
  / Cons: S01 から開くときも `/recipes` に移ることになり、「S02 を経由しない」という mealplan の要件と噛み合わない
- (c) ドロワーの幅をメインエリア全体に広げ、S02 と S01 の上に重ねたままにする
  — Pros: 下の画面がアンマウントされないので、状態を持ち回らなくてよい
  / Cons: ダイアログのままなので、フォーカスが閉じ込められ、サイドバーの操作と噛み合わない。
  S04 から戻るときは下の画面ごと組み立て直すので、S01 の開始日を URL に載せる必要は結局残る

**採用: (a)**。(c) は状態の持ち回りを避けられるように見えるが、S04 からの戻りで同じ問題が残る。
それなら画面として素直な (a) にし、状態の持ち回りを D2〜D4 で一度に解く。

### D2. 開いた元の持ち回り方

S03 と S04 は、パンくずの先頭と戻り先のために、開いた元の画面とその状態を知る必要がある。

**選択肢:**

- (a) S03 と S04 の search に `back` を持たせる ← 採用
  — 形は `{ to: "recipes", q?, sort? }` か `{ to: "mealplan", start? }` の判別共用体。S03 から S04 へ、S04 から S03 へ、そのまま引き継ぐ
  — Pros: 戻り先が URL だけで決まり、E2E からも追いやすい。S07 の `from` / `days` と同じ持ち方である
  / Cons: search に入れ子のオブジェクトが入る (TanStack Router は JSON で直列化するので動く)
- (b) ルータの履歴を 1 つ戻る
  — Pros: 状態を明示的に持たなくてよい
  / Cons: S04 でキャンセルして S03 に戻ったあと、パンくずで履歴を戻ると S04 に着く。保存後の戻り先とも規則が揃わない
- (c) モジュールの変数やストアに開いた元を置く
  — Pros: URL の形を変えない
  / Cons: 画面の外に隠れた状態になり、どの画面から来たかがコードを追わないと分からない

**採用: (a)**。型、zod スキーマ、`back` から戻り先の `navigate` 引数とパンくずの文言キーを作る関数を
`components/recipe/detail-origin.ts` にまとめる。`back` が無いか壊れているときは `{ to: "recipes" }` として扱う (zod の `.catch`)。

### D3. S02 の検索語と並び順の持ち方

S02 は S03 に移るとアンマウントされるので、今の `useState` では戻ったときに消える。

**選択肢:**

- (a) `/recipes` の search に `q` と `sort` を持たせる ← 採用
  — Pros: D2 の `back` にそのまま写せる。サイドバーのリンクは search を持たないので、開き直すと既定に戻る (spec のとおり)
  / Cons: 入力のたびに URL を書き換える
- (b) `useState` のまま、アンマウント前の値をモジュールの変数に退避する
  — Pros: URL の形を変えない
  / Cons: サイドバーから開き直したときに既定へ戻すための、別の後始末が要る

**採用: (a)**。検索欄の入力値は、URL の値ではなく検索欄の側の `useState` で持ち、変わるたびに `replace: true` で URL に書き写す。
URL の値で入力欄を直接制御すると、ルータの状態更新を待つ間に IME の変換中の文字が確定されたり消えたりするおそれがあるためである。
並び順の変更と検索語の変更は履歴に積まない (`replace: true`)。

### D4. S01 の開始日の持ち方

**選択肢:**

- (a) `/` の search に `start` (YYYY-MM-DD) を持たせる ← 採用
  — Pros: S07 の `from` と同じ形。サイドバーのリンクは search を持たないので、開き直すと今週に戻る (mealplan の要件のとおり)
  / Cons: 前後ナビゲーションのたびに URL を書き換える
- (b) localStorage に保存する
  — Pros: 期間長と時間帯表示と同じ置き場所になる
  / Cons: 「サイドバーから開くたびに今週」という既存の要件に反する

**採用: (a)**。`start` は受け取った日付を含む週の月曜に丸め、壊れた値は今週として扱う。
前後ナビゲーションと「今週」は `replace: true` で `start` を書き換える。

### D5. Esc キーで戻る仕組み

**選択肢:**

- (a) S03 の画面で `keydown` を購読し、削除の確認ダイアログが開いていないときだけ戻る ← 採用
  — Pros: 確認ダイアログの開閉は S03 自身の状態なので、確実に判定できる
  / Cons: S03 にダイアログを足したら、判定にも足す必要がある
- (b) Radix Dialog が Esc を処理したかを `event.defaultPrevented` で見分ける
  — Pros: ダイアログが増えても判定を足さなくてよい
  / Cons: Radix がイベントをどう扱うかという内部の振る舞いに依存する

**採用: (a)**。S04 では Esc キーで移動しない。入力欄が並ぶ画面で Esc を押すと、変換の取消のつもりで画面を離れる操作になりかねないためである。

### D6. S03 のレイアウト

上部に、パンくず、レシピ名 (見出し)、基本情報の行、「編集」「削除」のボタン (右寄せ) を置く。
その下を `lg` 以上では 2 列 (`grid-cols-[20rem_1fr]`) にし、左に材料、右に手順とメモを並べる。`lg` 未満では 1 列に積む。
手順とメモの列は、1 行が長くなりすぎないよう `max-w-3xl` に抑える。

ボタンを下端から上部に移すのは、手順が長いと下端までスクロールしないと編集に進めなくなるためである。
ドロワーのフッタに置いた理由 (高さが固定で、下端が常に見えていた) は、全画面では成り立たない。

### D7. 成り立たなくなるシナリオの扱い

「S03 レシピ詳細ドロワーの表示」「S03 の開閉」「S02 一覧から S03 を開く」「S01 献立カレンダーから S03 を開く」「レシピの削除」には、
ドロワーを前提にしたシナリオや、名前にドロワーを含むシナリオがある。

**選択肢:**

- (a) MODIFIED でシナリオを削除、改名する
  — Pros: 要件名が変わらず、E2E の describe 名も変わらない
  / Cons: `openspec validate` が「MODIFIED で既存のシナリオを落とした」として拒否する
- (b) シナリオ名を残し、中身だけ全画面の挙動に書き換える
  — Pros: 検査は通る
  / Cons: 「背景クリックで閉じる」のように、名前と中身が食い違う
- (c) 旧名の要件を REMOVED にし、中身を引き継いだ要件を新しい名前で ADDED する ← 採用
  — Pros: 削除の理由が REMOVED の Reason に残り、名前と中身が一致する
  / Cons: E2E の describe 名を改める必要がある

**採用: (c)**。`add-shopping-pantry-section` D5 と同じ扱いにする。
シナリオ名がそのまま通る「S03 から S04 編集画面への遷移」と「未保存変更のキャンセル確認」は、MODIFIED で文言だけ改める。

### D8. S04 のパンくずと未保存の確認

未保存かどうかは `RecipeEditForm` が持っているので、パンくずもフォームの中で描く。

**選択肢:**

- (a) `RecipeEditForm` に `breadcrumb: { label, onSelect }[]` を渡し、フォームが各 `onSelect` を未保存の確認で包む ← 採用
  — 確認ダイアログは今の「キャンセル」と同じものを使い、「破棄」で保留していた移動先を実行する
  — Pros: 確認の規則がキャンセルと 1 か所に集まる
  / Cons: フォームの props が増える
- (b) ルートの側でパンくずを描き、フォームから `isDirty` を上に出す
  — Pros: フォームはパンくずを知らない
  / Cons: 確認ダイアログの開閉がフォームとルートに分かれる

**採用: (a)**。今の `onCancel` も「S03 へ移る」という移動先の 1 つとして同じ仕組みに乗せる。

### D9. サイドバーの選択表示

S03 と S04 のパスは `/recipes/...` なので、S01 から開いてもサイドバーは「レシピ」を選択中として表示する。

**選択肢:**

- (a) パスのとおり「レシピ」を選択中にする ← 採用
  — Pros: サイドバーに手を入れない。サイドバーは「どの領域の画面か」、パンくずは「どこから来たか」と役割を分けられる
  / Cons: S01 から開いたとき、パンくずの「献立」とサイドバーの「レシピ」が食い違って見える
- (b) `back.to` が `mealplan` のときは「献立」を選択中にする
  — Pros: パンくずとサイドバーが揃う
  / Cons: サイドバーが search を読む必要があり、S03 の中から「レシピ」を押して S02 へ行く操作が選択中の項目の再押下に見える

**採用: (a)**。食い違いに不満が出たら (b) を後続で検討する。

### D10. パンくずの部品

**選択肢:**

- (a) shadcn の Breadcrumb を `components/ui/breadcrumb.tsx` に手動でコピーし、
  それを包む `components/layout/breadcrumb.tsx` を置く ← 採用
  — Pros: shadcn の手動コピーの運用と一致する。`nav` の `aria-label` と最後の項目の `aria-current="page"` が揃う
  / Cons: 使う部品はそのうち一部だけ
- (b) `nav` と `ol` で自前に書く
  — Pros: ファイルが 1 つで済む
  / Cons: 他の shadcn 部品と見た目の作法がずれる

**採用: (a)**。項目は `Link` ではなく `button` にする。S04 では押したときに未保存の確認を挟む必要があり (D8)、
memory history では `href` が意味を持たないので、S03 と S04 で同じく `onClick` から `navigate` する。

### D11. 削除後の移動

削除に成功したら、一覧と詳細のキャッシュを無効にし、トーストを出し、`back` の戻り先へ移る。
ドロワーでは閉じるアニメーション中の表示の切替を避けるために詳細を再取得しなかった (add-recipe-deletion D7)。
全画面では S03 がすぐにアンマウントされるので、詳細の再取得を止める理由は無いが、
アンマウント前に削除済みの表示へ一瞬切り替わるのを避けるため、`refetchType: "none"` はそのまま残す。

### D12. ワイヤー

S03 は、背後の画面にドロワーが重なる構造から、メインエリア全体を使う構造に変わる。
[docs/wireframes/README.md](../../../docs/wireframes/README.md) の例外 (画面構造そのものが変わった場合) に当たるので、
`S03_recipe_detail.v2.drawio.svg` を新しく作り、旧ワイヤーは初期案として残す。
S04 のパンくずは、画面の構造を変えない小さな追加なので、S04 のワイヤーは更新せず、この節を差分の記録とする。

## Risks / Trade-offs

- [S02 の検索欄を URL と結ぶことで、日本語入力の変換が崩れる]
  → 入力欄の値は検索欄の側の state で持ち、URL には書き写すだけにする (D3)。Windows 実機で IME 入力を確かめるタスクを置く
- [search の `back` が壊れていると、パンくずと戻り先が決まらない]
  → zod の `.catch` で `{ to: "recipes" }` に落とし、S02 に戻れる状態を必ず保つ (D2)
- [S01 から開いたとき、パンくずの「献立」とサイドバーの「レシピ」が食い違う]
  → サイドバーは領域、パンくずは来た道という役割分担にする。不満が出たら D9 (b) を後続で検討する
- [スクロール位置が戻らず、長い一覧で目的の行を見失う]
  → S02 は検索語を保つので、絞り込めば戻りやすい。不満が出たら後続で復元を検討する (proposal の引き継ぎ)
- [`openspec/specs/recipe/spec.md` の Purpose が「S03 詳細ドロワー」のまま残る]
  → delta では Purpose を変えられないので、archive のタスクに手での修正を入れる

## Migration Plan

スキーマとバインディングの変更は無い。保存済みのデータは変わらず、画面の遷移だけが変わる。
localStorage の `mealcycle.mealplan.*` は読み書きの形を変えない。
