## Context

動機は [proposal.md](proposal.md) の Why を、受け入れ条件は `specs/` の 3 つの delta を参照。

現状の実装で、この change に効く点は次のとおり。

- S07 の材料の合算と在庫の状態は、Go 側の `shopping.Aggregate` が決める。
  合算キーは「trim 後の食材名 + 単位」で、在庫も同じキーで合計してから `stockStatus(required, stock)` で 3 段階に丸める
- 量 0 の材料は特別扱いされていない。合計が 0 になった行は `stockStatus(0, stock)` で none か covered に落ち、
  フロントが必要量の列に「—」を出し、一括登録のダイアログで量を空にしている
- 行の識別子は、フロントの `itemKey` が作る「食材名 + 単位」である。購入済チェックの集合もこのキーで持つ
- 量と単位の表示は、S03 (`recipe-detail-drawer.tsx`)、S05 (`fridge-item-row.tsx`)、S07 (`shopping-table.tsx`) が
  それぞれ `formatAmount` の結果に単位を後ろから連結している
- フロントが Go の既定値を読む経路はまだ無い。`shopping-config.ts` のように、フロントに mirror を置いて手で同期している

## Goals / Non-Goals

**Goals:**

- 量を持たない材料の判定と合算を Go 側の 1 か所に閉じ、S07 の行の形 (`shopping.Item`) とバインディングを変えない
- 量と単位の表示順を 1 つの関数に集め、S03 と S05 が同じ規則で表示する

**Non-Goals:**

- 量る単位の一覧を実行時に変えられるようにすること (S09 で扱う)
- 量を持たない材料の行に、レシピの量を参考として添えること

## Decisions

### D1. 量を持たない材料を判定する場所

**選択肢:**

- (a) Go 側の `shopping.Aggregate` で判定し、合算と在庫の状態まで決める ← 採用
  — Pros: 在庫との突き合わせは Go 側にしか無く、判定と突き合わせが同じ場所に並ぶ。フロントは今の「量 0 なら —」の分岐のままで済む
  / Cons: `Aggregate` が量る単位の一覧を引数で受け取る必要がある
- (b) Go 側は今のまま単位ごとの行を返し、フロントで量る単位の行を束ねる
  — Pros: Go 側に手を入れない
  / Cons: 在庫の状態は単位ごとに算出済みなので、束ねた行の状態をフロントで決め直すことになる。在庫の一覧も別に要る

**採用: (a)**。`Aggregate(batches, stocks, measuringUnits)` とし、`ShoppingService` が `cfg.MeasuringUnits` を渡す。
domain が `config` を import しない既存の方針 (`DefaultVisibleMeals` を `[]string` で持つのと同じ理由) を保つため、
一覧は引数で渡す。

### D2. 量を持たない材料の行の形

**選択肢:**

- (a) 行の単位を空、必要量を 0 にする ← 採用
  — Pros: 量 0 の材料の既存の表示 (必要量「—」、ダイアログの量が空) がそのまま効く。単位も空なのでダイアログの単位も空になる。
  `shopping.Item` の形が変わらず、バインディングも変わらない
  / Cons: 行から元の単位 (大さじ) が読めなくなる。参考表示を足すときは項目を増やす必要がある
- (b) `shopping.Item` に「量を持たない」ことを示す項目を足し、単位は元のまま残す
  — Pros: 元の単位を画面に出せる
  / Cons: 大さじと小さじを束ねた行の単位を 1 つに決められない。バインディングと e2e の shim、`itemKey` も変わる

**採用: (a)**。元の単位を出す必要は proposal の Non-goals で外している。

### D3. 合算キーと量の足し方

量を持たない材料 (量 0、または単位が量る単位) は、合算キーを「食材名 + 空の単位」にし、足し込む量を 0 とする。
量のある材料は、これまでどおり「食材名 + 単位」をキーにして量を足す。

この決め方だと、同じ食材名で単位の無い量のある材料 (「塩 2」) があれば、量を持たない材料は同じキーに入り、その行に合算される。
行の必要量は量のある材料の分だけになるので、「塩 2」と「塩 小さじ 1」は必要量「2」の 1 行になる。
spec の「単位の無い量のある材料には量を持たない材料が合算される」はこの挙動を書いたものである。

**選択肢:**

- (a) 上記のとおり、単位の無い量のある行に合算する ← 採用
  — Pros: キーが「食材名 + 単位」のままなので、`itemKey` と購入済チェックが今の形で動く。量 0 と単位なしの量が同じ行になる今の挙動も保つ
  / Cons: その行の在庫の状態は単位なしの在庫だけで決まり、「塩 1 袋」の在庫は数えない
- (b) キーに「量を持たない」かどうかを足して、単位の無い量のある行とも分ける
  — Pros: 規則に例外が無い
  / Cons: 同じ「食材名 + 空の単位」の行が 2 つでき、`itemKey` が衝突する。D2 の (b) と同じくバインディングの変更が要る

**採用: (a)**。単位を書かずに量を持つ材料と、同じ名前の量る単位の材料が同じ期間に並ぶことは少なく、
キーの形を変える費用に見合わない。

### D4. 量を持たない行の在庫の状態

行の必要量の合計が 0 の行を「量を持たない行」とみなし、在庫は食材名だけで合計する (単位を問わない)。
合計が 0 より多ければ「在庫あり」、無ければ「在庫なし」とする。
在庫を食材名だけで合計した値を `stockStatus(0, stock)` に渡せば、既存の関数のまま none / covered に振り分けられる。
他の案として、量を持たない材料の判定結果を行ごとに覚えておく方法も考えた。
だが D3 の (a) により、単位の無い量のある行に合算された場合は量のある行として扱うので、行の必要量が 0 かどうかで判定するほうが spec と一致する。

### D5. 量る単位の一覧の置き場所

**選択肢:**

- (a) `internal/config/defaults.go` の `MeasuringUnits` に置き、フロントには mirror を置く ← 採用
  — Pros: 可変値を config に集める規約に沿う。S09 で設定項目にするときの差し替え点が 1 か所になる
  / Cons: Go とフロントで手動同期が要る
- (b) `internal/domain/shopping` に定数で置く
  — Pros: 変更が小さい
  / Cons: 表記ゆれ (大匙、tbsp) を足したい利用者が出たときに設定へ移す作業が残る。フロントの表示順と同じ一覧を別に持つことになるのは (a) と変わらない
- (c) `ConfigService` を新設してフロントに返す
  — Pros: 手動同期が要らない
  / Cons: S09 の proposal の範囲に踏み込む。サービス 1 つとバインディングの追加に対して、得るものが一覧 1 つだけ

**採用: (a)**。既定値は `[]string{"大さじ", "小さじ", "カップ"}`。
フロントの mirror は `frontend/src/lib/format-quantity.ts` に置き、`shopping-config.ts` と同じく source of truth が
`defaults_test.go` であることをコメントで示す。product.md §1 の可変値の表にも行を足す。

### D6. 量と単位の表示

`formatQuantity(amount, unit)` を `frontend/src/lib/format-quantity.ts` に置き、S03 と S05 から呼ぶ。

- 量が 0 なら単位だけを返す (S03 の既存の規則)
- 単位が量る単位なら「単位 量」の順にする
- それ以外は「量 単位」の順にし、単位が空なら量だけを返す

量の数値の整形は既存の `formatAmount` を使う。`formatAmount` は一括登録のダイアログの入力値にも使うので残す。
S07 の必要量の列は、量る単位の行が必ず「—」になるので、今の `formatAmount` と単位の連結のままでも表示は変わらない。
それでも表示の規則を 1 か所に揃えるため、S07 も `formatQuantity` に切り替える。
量 0 の行の「—」は S07 固有の表示なので、S07 側の分岐として残す。

他の案として、量る単位の表示順を各画面に書く方法も考えたが、3 画面で同じ規則を別々に持つことになるので採らない。

## Risks / Trade-offs

- [量を持たない材料の行は、瓶が空に近くても「在庫あり」になる]
  → 量の突き合わせは近似という S07 の前提のうちであり、量 0 の材料と同じ扱いになる。空になった在庫は S05 で消してもらう
- [「大匙」「tbsp」のような表記で書いた材料は、量のある材料のまま残る]
  → proposal の Non-goals どおり、一覧に足せば同じ扱いになる。S09 で利用者が足せるようにする
- [単位の無い量のある材料に合算された行では、別の単位の在庫を数えない (D3)]
  → spec にシナリオとして明記する。不満が出たらキーの形を変える案 (D3 の b) を検討する
- [Go の `MeasuringUnits` とフロントの mirror がずれる]
  → mirror のコメントで source of truth を示す。ずれても S07 の合算と在庫の状態は Go 側だけで決まり、影響は S03 と S05 の表示順にとどまる

## Migration Plan

スキーマとバインディングの変更は無い。既存のレシピと在庫のデータは書き換えず、表示と算出の規則だけが変わる。
