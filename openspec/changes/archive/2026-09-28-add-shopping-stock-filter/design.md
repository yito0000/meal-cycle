## Context

動機は [proposal.md](proposal.md) の Why を、受け入れ条件は [specs/shopping/spec.md](specs/shopping/spec.md) を参照。

S07 の現状は、`add-shopping-purchase` の実装後の形を前提にする。

- `ShoppingService.List` が返す材料の行には、在庫の状態 (`none` / `partial` / `covered`) がすでに付いている。
  並び順も Go 側で決まっていて、フロントは受け取った順に描くだけである
- 購入済チェックは `ShoppingPage` の `useState<Set<string>>` で、行のキー (`itemKey`) の集合として持っている。
  件数とダイアログの行は、集合を現在の `data.items` と突き合わせて数えている
- 見出しの全選択 (`ShoppingTable.toggleAll`) は、受け取った `items` の全キーで集合を置き換えている。
  絞り込んだ行だけを渡すと、隠れた行のチェックまで消える
- 日数プリセットの切替 (`shopping-period-picker.tsx`) は、`aria-pressed` を持つボタンを `fieldset` に並べた部品である

## Goals / Non-Goals

**Goals:**

- 絞り込みをフロントの表示だけで完結させ、Go 側とバインディングに手を入れない
- 絞り込みの条件判定と件数を 1 か所の純関数に置き、画面とテストが同じ定義を見る

**Non-Goals:**

- 絞り込みの結果に合わせて並び順を変えること。Go 側の並び順をそのまま使う
- 絞り込みの状態を他の画面と共有すること

## Decisions

### D1. 絞り込む場所

**選択肢:**

- (a) `ShoppingService.List` に絞り込みの引数を足す
  — Pros: フロントに判定が入らない
  / Cons: 絞り込みを切り替えるたびに再取得が走る。
  件数の表示には絞り込む前の全行が要るので、結局は全行を返すことになる
- (b) フロントで `data.items` を絞り込む ← 採用
  — Pros: 切替に往復が無い。件数も同じ配列から数えられる。Go 側とバインディングが変わらない
  / Cons: 状態と条件の対応をフロントに書く

**採用: (b)**。状態と条件の対応は `stock-filter.ts` の 1 か所に閉じる。
`StockFilter` 型は `"all" | "needed" | "covered"` とし、`matchesStockFilter(item, filter)` と
`countByStockFilter(items)` を置く。`needed` は `StockStatus.StockNone` と `StockStatus.StockPartial` に当てはまる。

### D2. 絞り込みの状態の持ち方

**選択肢:**

- (a) router の search param に載せる
  — Pros: S01 からの遷移で絞り込みを指定できる
  / Cons: 今のところ S07 の外から絞り込みを指定する導線が無い。
  サイドバーから開き直したときに「すべて」へ戻す spec と、search を引き継がない既存の遷移とが噛み合うかを確かめる手間が増える
- (b) `ShoppingPage` の `useState` で持つ ← 採用
  — Pros: 画面を離れれば消え、開き直すと既定に戻る spec がそのまま満たされる
  / Cons: 期間を切り替えても保つよう、チェックの集合とは別にリセットの条件を分ける必要がある

**採用: (b)**。チェックの集合は期間の切替で空にするが、絞り込みは期間の切替では戻さない。
期間を変えるのは「別の期間の買い足しを見る」操作であり、見たい行の種類は変わらないためである。

### D3. 見出しの全選択の範囲

**選択肢:**

- (a) `ShoppingTable` に表示中の行だけを渡し、全選択は渡された行のキーを集合に足す / 集合から引く ← 採用
  — Pros: テーブルは「受け取った行が表示中の行」という前提のままで済む。隠れた行のチェックは集合に残る
  / Cons: 置き換えから差分の更新に変わるので、`toggleAll` の実装を書き換える
- (b) テーブルに全行と絞り込みの条件を両方渡し、テーブルの中で絞り込む
  — Pros: テーブルが全行を知っている
  / Cons: 表示と絞り込みが同じ部品に混ざる。0 行のときのメッセージもテーブルの責務になる

**採用: (a)**。`toggleAll` は、表示中の行がすべてチェック済みなら表示中のキーを集合から除き、
それ以外なら表示中のキーを集合に足す。見出しのチェックボックスの checked / indeterminate も表示中の行だけで数える。
絞り込みが無いときは表示中の行 = 全行なので、`add-shopping-purchase` の挙動と一致する。

### D4. 切替の見た目と置き場所

日数プリセットと同じく、`aria-pressed` を持つボタンを `fieldset` に並べる。
ラベルは「すべて (4)」のように件数を括弧で添える。置き場所は材料テーブルの直上とし、期間の切替とは行を分ける。
期間の切替は材料と献立の両方に効くが、絞り込みは材料テーブルにしか効かないため、効く範囲の近くに置く。
他の案として select 要素も考えたが、選択肢が 3 つで件数も見せたいため、一度に全部見えるボタン列を選んだ。
部品は `shopping-stock-filter.tsx` に切り出し、`data-testid` を `shopping-filter-<種類>` とする。

### D5. 0 行のときの表示

絞り込みの結果が 0 行なら `ShoppingTable` を描かず、`pages.shopping.filter.no_match` の文言を出す。
絞り込みの切替と登録ボタンは残す。隠れた行にチェックがあれば登録できる状態を保つためである。
既存の空状態 (献立なし / 材料なし) は絞り込みより先に判定し、その場合は切替も出さない。

## Risks / Trade-offs

- [隠れた行にチェックが残っていることに気づかず、意図しない食材まで登録する]
  → 登録ボタンに件数を出しており、確認のダイアログには隠れた行も並ぶ。登録の前に一度は目に入る
- [「在庫なし・一部」で登録したあと、在庫が足りた行が消えるので、何を登録したかを画面で追えなくなる]
  → 件数のトーストが出るほか、「在庫あり」に切り替えれば登録した行を確かめられる
- [抜いた材料が「在庫なし」のまま残り続ける] → proposal の判断どおり、利用者が読み飛ばす運用とする。
  不満が出たら、作り置きごとの材料の上書きを別の proposal で検討する

## Migration Plan

スキーマとバインディングの変更は無い。`add-shopping-purchase` を archive したあとに apply する。
