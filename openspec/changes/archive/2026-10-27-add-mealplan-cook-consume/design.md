## Context

動機は [proposal.md](proposal.md) の Why を、受け入れ条件は [specs/mealplan/spec.md](specs/mealplan/spec.md) と [specs/fridge/spec.md](specs/fridge/spec.md) を参照。

- 「作った」印は `meal_plan_cooked (batch_id, recipe_id)` に 1 行で持ち、同じ作り置きの同じレシピの全行に効く。`MealPlanService.SetCooked` が付け外しする
- S01 のチェックボックスは `week-calendar.tsx` の `toggle-cooked` から `SetCooked` を呼ぶ。セルの中と「他 N 件」の一覧の両方が同じ経路を通る
- 在庫と材料の突き合わせの規則 (表記をそろえた食材名と単位、期限切れを除く、量 0 と量る単位は量を持たない材料) は S07 にだけある。
  そろえ方の関数は `add-fridge-staples` で `internal/domain/ingredient` に移る
- 在庫の行は `stock_items` の 1 行で、量は 0 より大きい値しか持てない (`CHECK (amount > 0)`)

## Goals / Non-Goals

**Goals:**

- 印の付け外しの経路と保存の形を変えずに、印を付けたあとの追加の手順として在庫の消費を足す
- 突き合わせの規則を S07 とそろえ、同じ在庫が S07 では「在庫あり」、消費では「在庫が見つからない」になる食い違いを作らない

**Non-Goals:**

- 減らした内訳の保存。保存しないので、印を外しても在庫は戻らない

## Decisions

### D1. ダイアログを開く時機

**選択肢:**

- (a) 印を保存してから候補を取り、候補があればダイアログを開く ← 採用
  — Pros: 印の保存は今と同じ 1 回の呼び出しで終わる。ダイアログを閉じても印は残るので、印と在庫の操作が独立する
  / Cons: 印だけ付けて在庫は減らさない状態が、「減らさない」を選ぶだけで作れる
- (b) 印を付ける前にダイアログを開き、確定で印と消費を同時に保存する
  — Pros: 印と消費を 1 トランザクションにできる
  / Cons: ダイアログを閉じると印も付かない。在庫の無いレシピでもダイアログを挟むか、分岐が増える

**採用: (a)**。印は「作った」という事実の記録で、在庫をどれだけ減らすかとは別の判断である。
(a) の Cons は、前日に作り置きを作って在庫を先に直してある場合のように、意図して在庫を変えない使い方にそのまま合う。

### D2. 候補を算出する場所

**選択肢:**

- (a) `FridgeService.PlanCookConsumption(ctx, entryID)` を足し、品の ID からレシピの材料と在庫を読んで算出する ← 採用
  — Pros: 在庫の突き合わせと減らす操作が同じサービスに収まる。`FridgeService` は DB を受け取るので、献立とレシピのリポジトリも作れる
  / Cons: `FridgeService` が献立とレシピのリポジトリに依存する
- (b) `MealPlanService` に足す
  — Cons: `MealPlanService` はリポジトリだけを受け取る作りで、在庫のリポジトリを足すとコンストラクタの形が変わる
- (c) フロントで、レシピの詳細と在庫の一覧を取って突き合わせる
  — Cons: 表記のそろえ方をフロントにも書くことになる

**採用: (a)**。`ShoppingService` も在庫のリポジトリを直接読んでおり、サービスが別 capability のリポジトリを読む形は前例がある。

### D3. 候補の割り当て規則

`internal/domain/fridge/consume.go` の `PlanConsumption(ingredients, stocks, stapleNames, measuringUnits, today, ...)` が純関数で割り当てる。

1. 量 0 の材料、単位が量る単位の材料、常備品と同名の材料を除く
2. 残った材料を「表記をそろえた食材名 + 単位」で合算する (同じレシピに同じ材料が 2 行ある場合)
3. 各材料に、同じ食材名と単位で期限切れでない在庫を、賞味期限の昇順 (期限なしは最後、同じ期限は追加日時の古い順) に並べる
4. 材料の量を、並べた順に在庫の量の範囲で割り当てる。割り当てきれない分は捨てる (在庫を負にしない)
5. 割り当てが 0 の在庫も行として返す (ダイアログで量を足せるようにする)
6. 在庫が 1 行も無い材料は `Missing` に食材名だけを入れる

賞味期限の近い順に割り当てるのは、利用者が古いものから使うと考えるのが自然だからである。
期限切れの在庫は S07 で使えないものとして扱っているので、ここでも候補に出さない。

### D4. まとめて減らす操作

**選択肢:**

- (a) `FridgeService.Consume([]Consumption{StockID, Amount})` を足し、全行を検証してから 1 トランザクションで反映する ← 採用
  — Pros: 途中まで減った状態を作らない。一括登録の `AddMany` と同じ作法
- (b) フロントから行ごとに `Update` と `Delete` を呼ぶ
  — Cons: 途中で失敗すると一部だけ減る

**採用: (a)**。検証は次のとおりとし、1 件でも違反があれば何も変えない。

- 在庫の ID が存在する
- 減らす量は 0 以上、その在庫の今の量以下
- 同じ在庫の ID が 2 回出ない

量が今の量と等しい行は削除し、それより少ない行は `amount` を減らして `updated_at` を進める。0 の行は触らない。

### D5. ダイアログの形

ダイアログは S07a (一括登録) と同じ部品で組み、材料ごとに見出し (食材名、レシピの量) と、その下に在庫の行を並べる。
在庫の行は「賞味期限 / 今の量 / 減らす量」の 3 列で、減らす量だけを入力欄にする。
「在庫が見つからない材料」は入力の無い一覧として最後に置く。

印を付けたあとで開くので、ダイアログを閉じる操作 (Esc、×、「減らさない」) はすべて在庫を変えないことと同じ意味になる。
フロントは `toggle-cooked` で印を付けた (`cooked` を true にした) ときだけ、`SetCooked` の成功後に `PlanCookConsumption` を呼ぶ。
戻り値の在庫の行が 0 件なら、ダイアログを開かない。

## Risks / Trade-offs

- [Risk] 同じ作り置きの印を外して付け直すと、ダイアログがもう一度開き、二重に減らせる
  → 初期値は今の在庫から算出するので、1 回目で減った分は 2 回目の初期値に入らない。それでも減らすかは利用者が決める
- [Risk] 献立の材料と違う名前で在庫を登録していると、候補に出ない
  → 「在庫が見つからない材料」に名前を出し、利用者が S05 で直すきっかけにする
- [Trade-off] 割り当てきれない分を捨てるので、在庫より多く使った事実は残らない。在庫は 0 より小さくならないので、記録の必要も無い

## Migration Plan

- スキーマは変えない。既存の印付きの品には何も起きず、この版から印を付けたときだけダイアログが開く
