## 優先度高：動作の不具合

### R21. 並べ替えたあとのセルで、品の削除と移動が失敗する（再現済み）

- [x] 対応済み（proposal: fix-mealplan-renumber-after-reorder）

3 品以上あるセルで並び順を変えたあと、上のほうの品を削除すると `UNIQUE constraint failed` で失敗する。
再現した手順は次のとおり。

1. 同じセルに A、B、C の順で割り当てる
2. B、C、A の順に並べ替える（`Reorder`）
3. 先頭の B を削除する（`Remove`）

原因は `removeRowTx` の詰め直しにある。
`UPDATE meal_plans SET position = position - 1 WHERE … position > ?` は、1 行ずつ主キーの重複を確かめながら進む。
`Remove` のコメントは「小さい position から順に上書きするので衝突しない」としているが、SQLite が行を処理する順は position 順とは限らない。
実際には挿入順（rowid 順）で処理され、並べ替えで挿入順と position 順が食い違ったセルでは、後ろの行が先に動いて衝突する。

同じ詰め直しは、D&D の移動（`MoveEntry`）と「作り置きから外す」（`SplitBatch`）にもある。
画面には汎用エラー（`errors.unknown`）が出るだけなので、利用者には原因がわからない。
「上へ移動」「下へ移動」が今日入ったことで、主菜、副菜、汁物の 3 品を並べ替える場面は増えるはずである。

直し方は 2 つある。

- `Reorder` と同じく、いったん大きな値へ退避してから詰め直す（局所的な修正）
- 行に ID を持たせ、並び順を主キーから外す（R25）

まず前者で止血し、リポジトリ層に「並べ替え後の削除、移動、外し」のテストを足す。

### R22. 「作り置きを広げる」が選んだとおりに反映されない

- [ ] 対応済み

統合ダイアログは対象日と時間帯の格子にチェックを付ける UI だが、反映の中身は旧 API 2 本（`CopyLeftover`、`CopyToOtherMeal`）の組み合わせである。
この継ぎ目で、次の 3 つのずれが起きる。

- **選んでいない日が埋まる**：同じ時間帯のチェックは「起点からいちばん遠い日までの連続 N 日」に読み替えられる（`computeCopyDays`）。
  月曜を起点に火曜と木曜だけを選ぶと、水曜にも入る。木曜だけを選ぶと、火曜と水曜にも入る
- **別調理が別時間帯に効かない**（再現済み）：`CopyToOtherMeal` は作り置き / 別調理の選択を受け取らず、常に起点と同じ作り置きに入れる。
  「別調理」を選んで別時間帯のセルにチェックすると、その行だけ起点と同じ作り置きになり、起点の行に枠色が付く
- **途中で失敗すると半端に残る**：セルごとに別々の呼び出しを順に投げるので、一部だけ反映された状態で止まりうる

1 つめは spec の「対象日 × 時間帯を自由に組み合わせて広げる」シナリオ（3 セルに追加される）と食い違う。
`computeCopyDays` のコメントは意図した挙動だと書いているが、チェックボックスの見た目はその約束をしていない。
このシナリオと「別調理を選ぶと各セルが独立した作り置きになる」の E2E は `test.skip` のままなので、テストでは気づけない。

対象セルの配列、作り置き / 別調理、追加 / 上書きを受け取って 1 トランザクションで反映する `SpreadEntry` を Go 側に 1 本作るのが筋である。
格子の行数が `LeftoverCopyPresets` の最大値に縛られている制約（spec に「別 proposal で拡張」とある）も、同時に外せる。
前回の R6（時間帯全体のコピーも同じダイアログに寄せる）は、この API ができれば入口を差し替えるだけで済む。

### R23. 「他の作り置きにまとめる」の候補に同じ作り置きが 2 つ出る（再現済み）

- [ ] 対応済み

同じ日の昼食と夕食にまたがる作り置きがあり、両方ともセルの先頭にあると、候補ダイアログに同じ作り置きが 2 行出る。
`ListMergeCandidates` は代表行を「日付 + 並び順」をつないだ文字列で選んでおり、時間帯を見ていないためである。
どちらを選んでも結果は同じなので実害は小さいが、別時間帯への持ち越し（昼に残りを食べる）はこの機能の主な使い道である。

### R24. OS がダークモードだと文字が読めなくなるおそれがある

- [ ] 対応済み

`index.css` は `prefers-color-scheme: dark` のとき `body` の背景を黒、文字を白に変える。
一方、画面の部品はすべて白や薄いグレーの背景を Tailwind のクラスで固定している。
その結果、色を指定していない文字だけが白になり、明るい背景の上に載る。
該当するのは、各画面の見出し（`h1`）、サイドバーのアプリ名、入力欄の文字（Tailwind の preflight が `color: inherit` にする）、テーブルのセルである。

Windows の WebView2 は既定で OS のテーマに従うので、ダークモードの PC では起動直後から起きると見ている。
実機では確かめていない。
ダークテーマを作る予定がないなら、`dark` のブロックを消して `:root { color-scheme: light; }` を置けば済む。

## 設計

### R25. 献立の行に ID がない

- [ ] 対応済み

`meal_plans` の主キーは `(date, meal, position)` で、フロントからの操作もこの 3 つ組で行を指す。
design.md §4 の MealPlan には `id` があるが、実装には入っていない。
ここから次の苦労が出ている。

- 詰め直しのたびに主キーを書き換えるので、R21 のような衝突が起きる
- `Reorder` は行を指せないので、レシピ ID の並びを受け取り、+1000 の退避と「同じレシピは古い並び順から割り当てる」規則で補っている
- `ListMergeCandidates` は代表行を文字列の連結で選んでいる（R23）
- 画面は操作のあと一覧を取り直すが、取り直しが終わる前の次の操作は古い並び順で行を指す。
  削除で 1 つずつ繰り上がった直後なら、隣の行に当たる

UUID の `id` 列を足し、`position` は並べ替え用のただの列にすると、上の 4 つはまとめて消える。
スキーマだけの proposal は作らない方針なので、R22 の `SpreadEntry` と同じ proposal に入れるのがよい。

### R26. 起動時の失敗が利用者に見えない

- [ ] 対応済み

DB を開けない、マイグレーションが失敗する、といった場合、`main.go` は `log.Fatalf` で終了する。
配布用ビルド（`-H windowsgui`）にはコンソールが無いので、利用者から見ると「ダブルクリックしても何も起きない」になる。
最低限、ネイティブのメッセージダイアログで DB の場所とエラーを出してから終了する。

これは前回の R18（バックアップの手段がない）とつながっている。
マイグレーションは起動のたびに本番の DB へ直接当たるので、スキーマを変える proposal（R25 を含む）を入れる前に、適用前の DB ファイルを隣にコピーしておく仕組みがあると安心できる。

### R27. エラーの受け渡しが文字列の部分一致に頼っている

- [ ] 対応済み
  （1 点目と 3 点目は proposal: fix-mealplan-renumber-after-reorder で対応した。2 点目は残っている）

小さな指摘を 3 つまとめる。

- `isForeignKeyErr` は `constraint failed` を含むエラーをすべて「存在しないレシピ」に読み替える。
  主キーの重複（R21）のような別の制約違反まで同じ扱いになりうる
- フロントは Go のエラーメッセージの部分文字列から i18n のキーを引く（`errorI18nKey`、`mapErrorToI18nKey`、`stockErrorOf`）。
  Go 側の文言を直すと、テストが通ったまま画面のメッセージだけが「不明なエラー」に落ちる。
  コード文字列の対応表を 1 か所に寄せ、Go 側のテストで全エラーを通すと気づける
- `internal/service/mealplan.go` の末尾に、`errors` の import を残すためだけの `var _ = errors.Is` がある。import ごと消せる

## UI/UX

### R28. S04 の編集中にサイドバーを押すと、確認なしで入力が消える

- [x] 対応済み（proposal: fix-recipe-form-and-list）

未保存の確認は「キャンセル」とパンくずにしか掛かっていない。
サイドバーの 4 項目は確認を通らないので、手順を書いている途中で献立を見に行くと、入力は黙って捨てられる。
TanStack Router の `useBlocker` で画面遷移そのものを止め、同じ確認ダイアログに流すのが確実である。

### R29. 「他 N 件」に隠れた品に触れない

- [ ] 対応済み

セルの表示件数を超えた品は「他 N 件」という文字になるだけで、開く手段がない。
4 週表示の上限は 2 品なので、主菜、副菜、汁物の 3 品目は、作った印も、削除も、レシピ詳細も使えない。
期間を 1 週に切り替えれば触れるが、それを示す手がかりは画面にない。
「他 N 件」を押すとそのセルの全品をポップオーバーで出す、という形が小さく済む。

### R30. S01 だけエラーと取り消しの作法が違う

- [ ] 対応済み

S05 と S07 は結果をトーストで知らせ、削除は「元に戻す」で救える。
S01 はエラーをカレンダー上部の赤い帯に出し、次の操作が成功するまで残る。
品の削除、時間帯全体のクリア、「作り置きから外す」は即時に実行され、取り消せない（前回の R9 が未対応のまま）。
エラーはトーストにそろえ、破壊的な 3 操作には「元に戻す」を付ける。

### R31. 「作り置きから外す」は選んだ行を消すことがある

- [ ] 対応済み

この操作は、作り置きの起点（いちばん古い日の行）だけを残し、ほかの行を削除する。
月、火、水に広げた作り置きの火曜で選ぶと、火曜と水曜が消える。
spec のシナリオどおりの動きだが、名前から受ける印象（この行を切り離す）とは逆である。

product.md と spec は、作り置きの行を動かす手順を「外して単独行にしてから D&D する 2 段操作」と説明している。
起点以外の行では、外した時点でその行が無くなるので、この手順は成り立たない。
次のどちらかに決めたい。

- 名前を「作り置きをやめる（最初の日だけ残す）」のように中身へ合わせ、D&D の説明を直す
- 挙動を「選んだ行だけを単独の作り置きに切り離す」に変える（前回の R7、作り置きごと日をずらす操作と合わせて考える）

### R32. S02 の更新日が生のタイムスタンプで、行をキーボードで開けない

- [x] 対応済み（proposal: fix-recipe-form-and-list）

- `RecipeTable` は `updatedAt` をそのまま出すので、更新日の列は `2026-10-13T03:21:45Z` のような UTC の文字列になる。
  S03 と同じ `yyyy/mm/dd`（ローカル日付）にそろえる
- 行は `onClick` を持つ `<tr>` で、フォーカスが当たらない。レシピ名をボタンにすれば Tab と Enter で開ける
- product.md §4 S02 は列を「名前 / タグ / 材料数 / 更新日」としているが、spec と実装は 3 列である

### R33. S04 の数値欄は、消してから打ち直せない

- [x] 対応済み（proposal: fix-recipe-form-and-list）

人数の欄は空にすると即座に 1 へ戻るので、Backspace で消して 4 と打つと 14 になる。
材料の量も同じ作りで、空にすると 0 が入る。
S06 の入力欄は入力途中の文字列をそのまま持ち、保存時に検証している。
S04 も同じ持ち方（`stock-form.ts` の方式）にそろえる。

### R34. spec の中で食い違っている箇所

- [ ] 対応済み

いずれも `openspec/specs/mealplan/spec.md` の「作り置き」まわりにある。

- 統合ダイアログの既定チェック：本文は「min(`LeftoverCopyPresets`) = 2 日」（火曜だけ）、シナリオは「火曜と水曜がチェック済み」。実装は火曜だけ

R32、R33、R34、R35 は、該当する画面や spec を次に触るときに一緒に直せる大きさである。
