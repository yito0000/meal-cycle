## 優先度高：動作の不具合

### R46. 「他の作り置きにまとめる」の探索範囲が、S09 で変えた日数に追従しない

- [x] 対応済み（proposal: fix-mealplan-merge-range）

`MealPlanRepo` はコンストラクタで `config.Defaults()` を抱え、`mergeDayRange` はそこから `LeftoverCopyPresets` の最大値を読む。
`ListMergeCandidates` と `MergeBatch` はこの値で ±N 日を決めるので、S09 で候補を変えても探索範囲は ±4 日のままになる。

settings の spec は、作り置きの日数の候補の反映先に「『他の作り置きにまとめる』の候補を探す日付の範囲」を挙げている。
add-settings-screen の design.md も、上限を 7 日にした理由にこの探索範囲を挙げており、意図はあった。
実装だけが追いついていない。

候補を「2」「7」にすると、広げる操作は 6 日先まで届くのに、まとめる候補は ±4 日しか探さない。
逆に「2」だけにすると、広げる操作は翌日までなのに、まとめる候補は ±4 日を探す。

CLAUDE.md の「サービスは `configSource` から読む」とも食い違う。
直し方は 2 つ考えられる。

- サービスが日数を計算し、`ListMergeCandidates` と `MergeBatch` の引数で渡す（`maxSpreadOffsetDays` と同じ位置に計算を寄せられる）
- リポジトリに `configSource` 相当を渡す

前者を勧める。
リポジトリが設定を知らずに済み、テストでも日数を直接渡せるためである。
spec の振る舞いは変わらないので、proposal を通さない不具合修正の大きさである。
回帰テストとして、候補を変えた設定で探索範囲が変わるサービス層のテストを足す。

### R47. まとめる候補の件数と日付が、探索範囲の内側の行だけで決まる（再現済み）

- [x] 対応済み（proposal: fix-mealplan-merge-range）

`ListMergeCandidates` は、`WHERE` で「同じレシピ」かつ「±N 日以内」に絞ってから、`COUNT(*) OVER` と `ROW_NUMBER() OVER` を掛けている。
前回の R36 と同じく、ウィンドウ関数は絞った後の行にしか掛からない。

再現した手順は次のとおり。

1. 10/19 の夕食に A を割り当て、10/20 から 10/22 の夕食へ作り置きとして広げる（4 行の作り置き）
2. 10/24 の夕食に A を単独で割り当て、その行でまとめる候補を開く

候補は「10/20 夕食 A (3 品)」と出る。
10/19 の行は 10/24 から 5 日離れているので、件数からも代表行からも落ちる。
利用者が見るのは、実際の作り置きと違う開始日と件数である。

直し方は、代表行と件数を作り置き全体（`batch_id` が同じ全行、レシピは問わないか同じレシピだけか）で求め、範囲の条件は「範囲内に 1 行でもある作り置き」の判定にだけ使う形である。
`ListPeriod` を R36 で直したときの相関サブクエリと揃えられる。
件数を同じレシピの行だけで数えるか、作り置き全体で数えるかは、ダイアログの「N 品」が何を指すかで決まる。
spec には件数の定義が書かれていないので、直すときに 1 文足すのが望ましい。

## 設計

### R48. S09 の制約の一部が、フロントに写しとして残っている

- [x] 対応済み（proposal: revise-settings-constraints）

`settings-form.tsx` の `SHOPPING_REQUIRED_DAYS`（7 / 14 / 28）と `SHOPPING_FALLBACK_DAYS`（7）は、Go 側の `settings.ShoppingRequiredDays` の写しである。
コメントで出典を指しているので、今すぐ壊れるものではない。
ただ、前回までの R17（既定値が複数か所に分かれている）と同じ形がまた 1 つ増えた。

`SettingsService.Get` の戻り値に「消せない日数」を足すか、制約だけを返すメソッドを足せば、写しは消せる。
R17 の残り（`spreadInitialFutureDays` がフロントで `maxSpreadOffsetDays` と同じ計算をしている点）も、同じ口で返せる。

あわせて、統合ダイアログは格子の判定に `ListPeriod(source.date, 1)` で 7 日分を取る。
`LeftoverDaysMax = 7` のおかげで格子（最大 7 行）と取得範囲が一致しているが、その結合はどこにも書かれていない。
上限を将来広げると、8 日目以降のセルだけ黄色の判定が抜ける（R37 と同じ症状）。
`validate.go` のコメントに統合ダイアログの取得範囲も挙げるか、ダイアログ側で行数から週数を計算する。

### R49. まとめるダイアログの日付が `2026-10-20` の形で出る

- [x] 対応済み（proposal: fix-mealplan-dialog-polish）

前回の R42 は統合ダイアログの日付を `Intl.DateTimeFormat` に揃えた。

### R50. S09 で保存せずに離れると、確認なしに変更が消える

- [x] 対応しない（spec どおり、保存せずに離れたら変更を捨てる）

S04 は `useBlocker` で離脱を確認するが、S09 は何も聞かずに入力を捨てる。
settings の spec は「保存せずに離れると変更は捨てられる」を Scenario にしているので、意図した挙動ではある。

それでも、同じアプリの中で「入力中のフォームを離れる」ときの扱いが画面ごとに違うのは気になる。
S09 は量る単位や言葉の欄でチップを足していく操作が多く、足し終えた後にサイドバーを押して消す場面は起こりやすい。
S04 と揃えるかは利用者が決めることなので、ここでは判断を求めるだけにとどめる。
揃えるなら spec の Scenario を差し替える proposal になる。

- [x] 対応済み（proposal: fix-mealplan-dialog-polish）

`week-calendar.tsx` は `SPREAD_EXPAND_STEP = 0` を渡しており、`SpreadBatchDialog` の `expandStepDays > 0` の分岐（ボタンと `setFutureDays` の加算）は描かれない。

prop、ボタン、`futureDays` の state、関連する文言キーを消すと、ダイアログが `initialFutureDays` だけで決まる形になる。
