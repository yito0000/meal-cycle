# 設計と UI/UX のレビュー（2026-09-25）

MVP 実装の途中（S01 / S02 / S04 / S05 / S06 / S07 は実装済み、S03 は未着手）で、設計と UI/UX を見直した記録。
アプリは起動しておらず、コードと `docs/` / `openspec/` を読んだうえでの指摘である。
対応したら各項目のチェックを入れ、proposal に取り込んだ場合はその名前を追記する。

コード位置はファイル名と関数名で示す（行番号はすぐずれるため書かない）。

---

## 全体所感

設計判断の粒度と記録の丁寧さは高い。
たとえば「作り置き = `batch_id`」でペルソナの使い方をデータモデルに落とし込めているし、S05 は削除を確認なしで行い、代わりに元に戻す手段を用意している。

ただし、完了した 17 の proposal のうち 11 本が献立（mealplan）系である。
S01 の磨き込みが先行した結果、[product.md §1](../product.md) の「3 つの起点」のうち 2 つ（これから料理する、買い物）の経路がまだ途中で止まっている。

## 優先度高：今後の方針に影響するもの

### R1. 買い物リストを外出先で見る手段がない

- [ ] 対応済み

完全ローカルのデスクトップアプリなので、スーパーの店内では S07 を開けない。
買い物リストは、スマホで見る、紙に印刷するなど、PC の外に持ち出せて初めて実用になる。
外部との通信をしない方針のままでも、次の手段なら実現できる。

- **テキストでクリップボードにコピーする**（LINE やメモアプリに貼れる）。いちばん安価で効果が大きい
- 印刷用 CSS（`window.print()`）
- ローカル LAN 上に QR コードで一時的に配信する（ローカル完結の原則とぶつかるので要検討）

これを踏まえると、`add-shopping-purchase`（購入済みチェック）の前提も変わる。
チェックを付ける場面は店内ではなく、帰宅後に「買ったものを在庫に入れる」ときになるからである。
そうであれば、中間ステップは「チェックした品目の量と賞味期限を表で直してから一括登録する」画面として設計し直すのが自然である。
現在の方針（[product.md §4 S07](../product.md)）は賞味期限を空のまま登録し、あとで S05 から入れる流れなので、同じ入力を二度やることになる。

### R2. レシピ削除が献立の履歴を消してしまう

- [x] 対応済み（`add-recipe-deletion` で論理削除を採用。献立の履歴は残る）

`meal_plans.recipe_id` には `ON DELETE CASCADE` が付いている（`internal/storage/sqlite/migrations/00003_meal_plans.sql`）。
このままレシピ削除（`add-recipe-deletion`）を実装すると、そのレシピを使った過去と未来の献立が黙って消える。
消えるのは表示だけではない。
MVP 後の提案機能のうち「久しぶりに」は献立の履歴から計算するので、その根拠データも失われる。

削除機能に着手する前に、次のどちらにするかを決める。

- **論理削除（アーカイブ）にする**。一覧やピッカーからは隠し、履歴には残す
- 物理削除を残すなら、「このレシピは N 件の献立で使われています」と件数を示して確認する

### R3. レシピと在庫で食材名の表記が揃わない

- [ ] 対応済み

食材名の候補補完は、冷蔵庫の入力欄にしかない。
S06 の追加行はレシピの材料名を候補に出すが、S04 の材料行（`RecipeIngredientRow`）はただのテキスト入力 3 つである。
一方、S07 は在庫を「食材名 + 単位」の完全一致で突き合わせる。
そのため「玉ねぎ / たまねぎ」「1 個 / 1 玉」のような揺れがあるだけで、在庫があっても「在庫なし」と表示される。

食材マスタ（S08）を作る前でも、次の 2 手でかなり改善できる。

- S04 の材料名に、S06 と同じ候補入力（在庫名 + 既存の材料名）を付ける
- 突き合わせのときだけ表記を正規化する（ひらがなとカタカナ、全角と半角の統一）

### R4. 「予定」と「実際に作った」の区別がない

- [ ] 対応済み

`meal_plans` には、実際に作ったかどうかを記録する列がない。
「久しぶりに」軸が使う「最終使用日」も、予定と実績の区別がないまま計算されることになり、未来の予定まで数えてしまう。

`add-mealplan-cook-consume`（作った印を付けて在庫を減らす）を提案機能の前提に置く順序は妥当である。
そのときは MealPlan に `cooked_at` のような状態列を足すことになるので、この変更をどの proposal に含めるかを先に決めておく。

### R5. 押せるのに動かないメニューがある

- [ ] 対応済み

> `add-recipe-details` で「この品のレシピ詳細を見る」は S03 ドロワーを開くようになった（add-recipe-details の design.md D8）。
> 「並び替え」は未対応のため、チェックは付けていない。

S01 の `WeekCalendar` で、次の 2 つのメニューは押すと汎用エラー（`pages.meal_plan.errors.unknown`）を出す。

- 品の `⋯` にある「この品のレシピ詳細を見る」（`handleEntryAction` の `view-detail`）
- 時間帯の `⋯` にある「並び替え」（`handleMealAction` の `reorder`）

利用者から見ると、機能が未実装なのではなく、壊れているように見える。
実装するまではメニューから外す。
並び替えは D&D ですでにできるので、項目ごと削除してもよい。

「これから料理する」起点（当日のレシピを見る）は S03 がないと成り立たない。
次に `add-recipe-details` に取りかかる判断は、この点からも妥当である。

## S01 献立カレンダー

### R6. 作り置きのコピーに入口が 2 つある

- [ ] 対応済み

品の `⋯` から開く「作り置きを広げる」は、対象日と時間帯の格子に、作り置き / 別調理、衝突時の扱いまで選べる。
時間帯の `⋯` から開く「連続 N 日コピー」は、日数を選ぶサブメニューとコピー方法ダイアログの組み合わせである。
中身は同じ操作なのに、UI が 2 系統ある。
`revise-mealplan-leftover-ux` で品の側は統合済みなので、時間帯の側も「時間帯内の全品を広げる」ダイアログに寄せると、覚えることが減る。

### R7. 作り置きの行を D&D で動かせない

- [ ] 対応済み

現状は、一度「作り置きから外す」で単独の行に戻してからドラッグする 2 段の操作になっている。
実際に多いのは「作り置き全体を 1 日後ろにずらす」操作だと思われる。
作り置きの行を掴んだら作り置き全体を同じ日数ずらす、という挙動を検討する。

### R8. 作り置きの色が隣どうしで重なりうる

- [ ] 対応済み

`colorForBatch`（`batch-color.ts`）は `batch_id` のハッシュを 3 色に振り分けている。
`BATCH_COLORS` のコメントには「3 色ローテーション」とあるが、実際には作り置きが 2 つしかなくても 1/3 の確率で同じ色になる。
表示中の期間で作り置きを登場順に並べ、その順に色を割り当てるほうが確実である。
また、ドラッグ中の ghost の色（emerald）が作り置きの色の 1 つと同じである。

### R9. 破壊的な操作を元に戻せない

- [ ] 対応済み

S05 は即削除して元に戻せる方式だが、S01 の品の削除と「時間帯全体をクリア」は即時に実行され、元に戻せない。
破壊的な操作の扱いはアプリ全体で揃える。

### R10. 提案機能の前に安価に足せるもの

- [ ] 対応済み

レシピ選択ダイアログ（`RecipePickerDialog`）は名前の検索しかできない。
各レシピに「最後に使った日」を添えて並べ替えられるだけで、「久しぶりに」軸の簡易版として機能する。
週プリセット（`add-mealplan-suggest-week-preset`）より先に、「先週の献立をまるごとコピー」を入れるほうが安く作れて効きやすい可能性がある。

## S02 / S03 / S04 レシピ

### R11. S03 ドロワーの置き場所

- [x] 対応済み

> `add-recipe-details` でドロワーを呼び出し元から独立した部品にした。S02 は search param `detail`、S01 はローカル state で開閉する
> （add-recipe-details の design.md D2 / D8）。S02 の行クリックもドロワーを開く挙動に切り替えた。

S03 は S01 からも開く仕様なので、S02 のルートに閉じた部品にすると S01 から使えない。
memory history のままでも、ルート共通の search param（`?recipe=<id>`）かグローバルな state で開閉すれば、両方の画面から同じ部品を使える。
`add-recipe-details` の design.md で決める。

なお、現状は S02 の行をクリックすると直接編集画面に飛ぶ（`RecipesPage` の `onRowClick`）。
S03 の実装でドロワーを開く挙動に切り替える。

### R12. 手順の持ち方がドキュメントと実装で違う

- [ ] 対応済み

手順は単一の TEXT 列（`recipes.steps`）だが、product.md §4 S04 は「行追加型のテキストエリア + 上下ボタン」、design.md §4 は `steps: string[]` と書いている。
Markdown で書く運用に決めたのなら、ドキュメントを実装に合わせる。

### R13. S10 レシピ検索は独立画面にしなくてよい

- [ ] 対応済み

20〜50 品という規模なら、S02 の検索対象にタグと材料名を加えるだけで足りる。
product.md §2 の S10 を「S02 の検索拡張」に置き換えることを検討する。

## S05 / S06 冷蔵庫

### R14. 使ったときの操作が重い

- [ ] 対応済み

インライン編集、元に戻す操作、期限切れの表示はよくまとまっている。
気になるのは使ったときの操作で、減らすには編集モードで数値を書き換えるしかない。
`cook-consume` が入る前のつなぎとして、行に「使い切った」（削除して元に戻せる）ボタンだけでもあると、在庫の精度が保ちやすくなる。
「使い切り」提案が当てになるかどうかは、この在庫の精度に左右される。

## S07 買い物リスト

### R15. 在庫の量が見えない

- [ ] 対応済み

在庫の列は状態しか示さないので、「一部在庫あり」のときに何がどれだけあるのかわからない。
在庫量を併記する（例：「一部（200 g）」）。

### R16. 人数を考慮しないことが仕様に書かれていない

- [ ] 対応済み

必要量はレシピの分量をそのまま合計しており、人数（`servings`）は考慮していない。
作り置きで回す前提なら問題ないが、shopping の spec に明記しておくと、あとで迷わずに済む。

## 未実装の画面（S08〜S10）と横断的な論点

### R17. 既定値が 3 か所に分かれている

- [ ] 対応済み

S09 を待つあいだに、既定値の置き場所が次の 3 か所に分かれている。

- Go の `config.Defaults()`
- フロントに手で写した値（`MEALPLAN_DEFAULTS`、`RecipesPage` の `HIGHLIGHT_MS`）
- localStorage（S01 の表示設定）

S09 の画面を作る前でも、`ConfigService.Get()` を読み取り専用で先に入れれば、手で写す作業はなくせる。

### R18. バックアップの手段がない

- [ ] 対応済み

データはローカルにしかないので、DB ファイルを失うとすべて失われる。
S09 の import / export を待たなくても、最低限「DB ファイルの場所を開く」「バックアップを書き出す」があると安心できる。
MVP 寄りに前倒しすることを検討する。

### R19. S08 食材マスタは軽いものから始める

- [ ] 対応済み

R3 の対策（候補補完 + 正規化）で不満が残ったときに、「別名（alias）の辞書」程度の軽いものから始める。
単位の換算まで踏み込むと、重さが一段変わる。

## R20. 実装とずれているドキュメント

- [ ] 対応済み

CLAUDE.md で load-bearing と位置づけているわりに、design.md は初期案のまま残っている部分が多い。

- **§4 データモデル**：Ingredient マスタ、`steps: string[]`、MealPlan の `id`、`meal: "other"` が実装と違う。`batch_id` の記載もない
- **§4 議論ポイント**：「食材マスタは最初から分ける方針」とあるが、実装は自由テキスト（R3）
- **§6 ディレクトリ構成**：`recipe_service.go` や `domain/stock/` と書かれているが、実際は `service/recipe.go` と `domain/fridge/`
- **§3 と §5 の「実装時に確定」**：ルータ（TanStack Router）、マイグレーション（goose）ともに確定済み
- **§8 の proposal 順序案**：実際の順序や命名（`add-recipe-edit`、`add-mealplan-*` の細分化など）と合っていない

`add-recipe-details` の proposal を切る前に、§4 だけでも実装に合わせて直しておくと、AI に proposal を書かせるときに古い前提へ引きずられずに済む。

## 進める順番の案

費用対効果の高い順に、次の 3 つを候補とする。

1. `add-recipe-details`（S03。R5 の行き止まりも解消できる）
2. S07 のテキストコピー（R1）
3. S04 の材料名の候補補完（R3）

R2（レシピ削除）と R4（作った印）はスキーマに関わる判断なので、該当する proposal を切る前に方針を決める。
